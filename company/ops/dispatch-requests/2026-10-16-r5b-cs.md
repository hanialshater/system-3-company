## Ruling W-1352 · kmp-never-steps-back: add a way back to the start (milestones kept)
What happens (Demo.tsx on main): the reveal needs `saw-miss` and `both-done`. `saw-miss` is reached only when the run is **stopped** on a miss (k in 4, 6, 8, 10, 12). "Run to end" pressed first animates k up to 24 and never stops on a miss. At k = 24, `over` disables all three controls. `saw-miss` can never be reached, and only a reload gets the learner out.

Decision: **keep both milestones and add a Start over control.** I keep `saw-miss` because v5 (r6) added it deliberately: learners who only ran to the end never looked at a miss, and a miss is where the lesson's insight is (the boxed 2 keeps two A's). Removing the gate would undo a learner finding. The fix:
1. A **Start over** control that sets k back to 0 and stops any run. It can be used whenever k > 0 and no run is going. Milestones already reached stay reached: `useMilestones` keeps them in a ref, and `reach` ignores repeats. After Start over, "To next miss" stops on miss 1 (k = 4), and the reveal unlocks.
2. Placement, which I suggest without deciding it (lane 6 owns the look): the row should stay at three buttons on a phone. "Run to end" shows as "Start over" while `over` is true. If the builder finds that relabelling a button in place confuses the walk, a fourth control is acceptable. The builder records the choice in build.md.
3. When `over` is true and `saw-miss` has not been reached, the caption line should give one instruction: "Start over, then stop on a miss to see what the reuse lane keeps." This is an instruction, not a factual claim. Any sentence the builder writes that states a fact is a claim in meta.json, recorded `unverified`.
4. The reveal text, the predict and claims c1 to c8 do not change.

Why not the alternatives: (a) Making "Run to end" pause at the first miss would make the button do something its label does not say. (b) Letting `both-done` alone unlock would remove the r6 fix. (c) Making "Run to end" usable only after a miss would hide a control's purpose behind an order the learner cannot see.

## Ruling W-1353 · rolling-hash-window: the long slide stops at every flag that has not been checked
What happens (Demo.tsx on main): from window 0 (FEBCD, sum 20, no flag), "Slide to end" jumps straight to window 8 (ABCDE). It slides past window 1 (EBCDA, sum 15), which is flagged and never checked. "Check letters" at window 8 is a true match, so `false-flag-checked` is never reached. Then all three controls are disabled.

Decision: **"Slide to end" stops at the next window that is flagged and unchecked. Rename it "Slide to next flag".** This is more than a fix for the dead end. As built, the long slide breaks the lesson's own rule ("a flag must be checked before moving on", the `blocked` line, which already stops the one-step Slide). It also misrepresents the algorithm: a rolling-hash search never moves past a window whose hash matches without checking it. So the shortcut was teaching against claim c4 ("equal sums still need a check").
- From window 0 it stops at window 1 (the flag must be checked; Slide and the long slide are blocked until the learner checks it). From window 1, after the check, it goes to window 8, the only other window with sum 15 (c1: 20, 15, 16, 20, 18, 16, 18, 16, 15). So for the rest of the lesson it still means "to the end".
- The label: "Slide to next flag" fits the button's job on every press, and it echoes kmp's "To next miss". The look is lane 6's. If the builder keeps "Slide to end", the stop at window 1 must say why, for example "Stopped: window 2 is flagged. Check the letters." The existing flag message already says "Flag: the sum equals 15. Check the letters."
- The jump caption ("N slides × 2 letters …") stays correct, because it counts the slides actually taken.
- The reveal's false-flag sentence (`checks[1] && !checks[1].ok`) now always shows. It is c4, which is already verified. c1 to c6, the predict and the reveal text do not change.
- After the fix, reverse order (long slide → check → Slide → long slide) reaches both milestones. I traced this by hand on the code: it is a derivation, not a measurement. B1's done check measures it.

## Ruling H · no publish hold for either lesson (with a trigger)
Neither lesson goes into publish-holds.json now. Reasons:
1. Both locks need the shortcut button pressed **before** the step-by-step path. Each lesson's explore hint names the step-by-step path first ("Stop on a miss … Then run both to the end"; "Slide the window one letter, check the window it flags, then slide to the end"). The forward, DOM-order walk passes (the existing contract and both 2026-10-14 QA records).
2. The lock costs a stuck learner a reload. It shows no false sentence and harms no learner data. It is a P1 defect, not an emergency under §4.
3. A hold unpublishes a live lesson, which means a founder ask and a feed change. That costs about as much as the fix, which is about 20 lines in each of two files, in one build.
4. A hold removes the lesson for every learner, and most of them never hit the lock. A fix removes the lock and keeps the lesson.
