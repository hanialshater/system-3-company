## 5. Code notes for the principal engineer (not a verdict)

1. The engineering read in the PR (`company/engineering/readiness/2026-10-16-algorithms-200.md`, "Capacity") was at 150 wrappers in 15 topics; the last 50 lessons and 5 topic modules were not read. It also says integrated `verify`, the server lifecycle and independent QA "must be appended before W-1566 closes". None of that is in the PR.
2. `tests/algorithms/*.test.mjs` is not in `package.json` (`verify` or a `test:algorithms` script), so CI and `verify` never run it. PR #5 had the same gap (PE M1 there).
3. `src/components/algorithms/AlgorithmState.ts`: nothing checks that `cases[1]` differs from `cases[0]` at the frame the learner sees; that is how 3 lessons reached QA with a dead "Try another". A test over all 200 specs would catch it earlier (the PR #5 M2 payload-test pattern).
4. `src/app/catalog/page.tsx` renders the Algorithms section on the live map whatever the lessons' status. In production, drafts are hidden, so after a deploy the map shows "200 planned lessons across 20 topics" and 20 groups marked "Not yet visible". That is a product/design question for cm-cs and design-lead, and an accessibility one (W-1571), not a mechanical defect.
5. `tools/serve.sh`: `-H 127.0.0.1` makes every lane's local server loopback-only. The QA harness uses `localhost`, so it is unaffected here (feed and contract ran through `next start`, not `serve.sh`); any evaluator reaching a server from another host would lose access. The Tools row needs tools-lead or the owning engineer; I folded it into W-1568.
6. `src/{components,lib}/algorithms/**` has no `paths.json` rule, so `tools/readiness.mjs` would call it tier 1. Adding a `shared-engine` rule is the principal engineer's call.
