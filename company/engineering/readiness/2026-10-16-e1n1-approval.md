What the diff does: `fold` takes `<spool>/fold.lock` with O_EXCL and writes its pid there. If a live pid holds the lock, the fold refuses with exit 2 and names that pid. A lock left by a dead pid, or one holding no pid, is taken over only under a second O_EXCL file, `fold.lock.takeover`. The fold removes the stale lock only if the lock still holds the pid it judged dead. A `*.folding-<pid>` file is adopted only when `process.kill(pid, 0)` says the pid is dead (ESRCH). F2 is closed from both sides. On the fold side, each renamed file is re-read once it has stopped growing for 100 ms, and any late ids are folded in. On the writer side, `spoolAppend` (the hook's `add --spool` path) writes the line again if the path no longer points at the inode it wrote to. I read the takeover sequence for the case where two folds find the same dead lock. Whichever gets the takeover file removes the lock. The other one then sees either no lock or the winner's live pid, and refuses. Two holders of the takeover file at once would each only remove a lock that still holds the dead pid, so that case is harmless too.

S2 (`tools/ops-health.mjs`, `tools/rituals-due.mjs` now read the log through `readJsonlFile`) is read-only, tier 1, and outside the hook's file list. I read it and have no objection. It does not count as "a change to the files above".

### F5 (tools-lead, does not gate wiring): fold overflows the stack on a large spool file

`fold` collects events with `events.push(...r.events)` (tools/events.mjs line 194 at c449e23, and `bad.push(...)` at 195 and 218). `readSpool` in tools/lib/events-spool.mjs line 75 does the same, and that function feeds `fold --dry`, metrics and dispatch-check. Node 22 throws `RangeError: Maximum call stack size exceeded` once a single spread passes roughly 120,000 elements (100,000 works, 150,000 fails). I hit it in a run of 2 × 200,000. The fold had renamed the file to `*.folding-<pid>` and then threw before it wrote anything. The lock was released, and the log plus that file together held all 400,000 ids exactly once. So it fails safe, but every later fold adopts the same file and throws again, which means folding is stuck until the code changes. This code was already there at 23c6255. The hook writes a few events an hour, so it cannot happen at that rate. Fix: use a loop, or `for (const e of r.events) events.push(e)`, in all four places, and add a test with a 200,000-line spool file. This needs no readiness round. Tell me the commit, and I will rerun the test.
