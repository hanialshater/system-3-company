### 1. What can fail
- Neon unreachable or cold: sign-in, sync, export and delete answer 500 with a fixed log line. Lessons, local progress and the beacon are unaffected (nothing on a page waits on `/me`). An unreachable store is retried on the next request.
- **Schema mismatch** (a migration not applied, or the wrong database): Better Auth's run-time check fails closed and **caches the mismatch until the instance restarts**, so every account route answers 500 until a redeploy (hand QA note, finding 1). Mitigation: migrations before the deploy that turns accounts on.
- Email: no key on production refuses to send (500 on `start`); Resend down gives 500 on `start`.
- A `BETTER_AUTH_TELEMETRY*` variable set anywhere: auth refuses to construct (A-5), so account routes answer 500 rather than send telemetry.
- Secret leak (`BETTER_AUTH_SECRET`): sessions can be forged; rotate and redeploy, which signs everyone out.
- A bad migration: `down` files exist and are tested (test 26); data needs a Neon restore inside the plan window, then the tombstone replay (EDD-008 §7).

### 2. How we would know
- Today: the fixed log lines (`account <route>: failed [sqlstate=XXXXX]`, `better-auth error`) in Vercel function logs, which on Hobby live about an hour and have no drain or alert (A-7). **Merge minimum (A-7):** the post-deploy smoke asserts `GET /api/account/me` is 404 on production until go-live; the ready-made check is `ACCOUNTS_BASE_URL=<prod> ACCOUNTS_EXPECT=off node --test tests/accounts/built-routes.test.mjs` (release-manager to wire into the smoke). Go-live: a named synthetic is still owed (A-7).
- Expired rows waiting for the purge: `tools/db-deletion-check.mjs --oldest-expired` (A-15, principal-engineer-ops runs it).

### 3. How to roll back
- **Switch off:** set `ACCOUNTS_ENABLED` to anything but `on` **and redeploy** (R3; a variable reaches only new deployments). Time to off = founder reachable + a Vercel build (not measured) + promote. Faster options are the release manager's and platform-engineer's (A-3: Instant Rollback to a pre-flag deployment, or a firewall rule on `/api/account/*`). Likes and counts have their own switches and the same redeploy rule.
- **Code:** a revert; nothing outside the account paths depends on it (`progress.ts` works with no sink).
- **Schema:** `node tools/db-migrate.mjs down --confirm-drop` (002 then 001), tested locally (test 26). Run on the **test** project first.
- **Order at go-live (A-8, A-14):** create the separate Production project (Frankfurt, Production only, branching off) → read `SHOW server_version` (must be ≥ 16; `db-migrate` refuses otherwise) → apply 001 and 002 by hand with accounts off → set the Production-only variables → A-4, A-5 checks → G1 to G6 → the founder-approved deploy that turns accounts on. A migration applied to a database already serving needs a redeploy before the routes see it (§1).

### 4. Capacity
- Storage about 6 KB per active learner plus 50 bytes per like or save; Neon Free's 0.5 to 1 GB holds tens of thousands of learners. Compute per request not measured (A-10, needs a preview). Pool `max` 3 per instance.
- Function size of the auth route: not measured on this rebuild (the spike measured 9.11 MB on the old branch).
- First-load JS: `/` +743 B gzip, `/d/<slug>` +573 B gzip (under the 1 KB C9 ceiling), with no account or library string in any first-load script (hand QA note).
- With accounts **off**, each page load makes one `GET /api/account/me` that answers a 404 the browser and CDN may keep 5 minutes. That is at most one function call per visitor per 5 minutes.
- Resend free quota: unverified.

### 5. Security
- Secrets per environment, never in git. Cookie `s3c.session_token`, `Path=/api/account`, `HttpOnly`, `SameSite=Lax`, `Secure` with the `__Secure-` prefix on https. No cookie cache.
- CSRF: our own state-changing routes check `Origin` (and `Sec-Fetch-Site`) and `start`, `merge`, `progress`, `delete` require `application/json` (C7); Better Auth's origin check covers sign-out. Only two library endpoints are routed at all (verify, sign-out).
- Rate limits: `start` 5 per 60 s per IP and per email; verify 30 per 60 s per IP (F-f, done early); like writes 60 per account per rolling day. Limiter keys are HMAC under a per-instance random key (M6); per instance, in memory.
- Tokens: magic-link token hashed at rest, 300 s, single use. Session tokens are stored plain (database access equals session access; Neon access is as wide as the Vercel team, ADR-009).
- Telemetry refused by construction (A-5). Logs: fixed text and SQLSTATE only (A-6, test 23 and S8).
- `npm audit --omit=dev`: 0 vulnerabilities on this lockfile (2026-10-17).
