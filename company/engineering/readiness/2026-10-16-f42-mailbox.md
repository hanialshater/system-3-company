The package.json line waits for principal-engineer-ops. It changes no dependency. It adds one script and one step to `verify`, just as F-39's `test:memory` did. The rest is tier 1 by paths.json (default rule; company/** is tier 0). It does not touch deploy, the event API, auth or learner data. No protected path is touched: tools/company.mjs is unchanged, so `company status` does not show mailboxes, and `node tools/mailbox.mjs status` does.

1. **What can fail.** (a) A false refusal: the lane parse reads prose, so a lane whose cell names no role id (lane 4 today) cannot ask by mail. That fails closed and only affects agents. (b) A double start: two drains could start the same request. The `claim` marker is O_EXCL, and M1 refuses a claimed request, so the second start fails at the check. That only holds if the chief of staff runs the check before every start. (c) Worst case, an out-of-lane run through a hand-written message file: M1 re-checks the lane in every slot mode, so this also needs someone to skip dispatch-check. Only agents see any of these failures.
2. **How we would know.** `mailbox.mjs status` shows unclaimed requests and unread reports. `drain` prints REFUSED with the reason. dispatch-check prints `M1 mailbox lane: …` as a FAIL. There is no alert for an idle mailbox (objection 2 in the decision stays open). The meter is the chief of staff running `status` every turn, per the runbook.
3. **How to roll back.** `git revert <sha>` (seconds, no founder needed). The spool is gitignored, so a revert leaves the message files on disk and loses no history: the event log holds the record. Without the tool, dispatch falls back to batch files and standing orders, which are unchanged.
4. **Capacity.** Small text files under company/ops/mailboxes/. One `git rev-parse` per CLI run (a few ms). M1 adds one directory scan to dispatch-check. `test:mailbox` takes 8 s (7 tests, mostly process spawns with the git stub).
5. **Security.** No routes and no network. `--from` is self-asserted: a role can send as another role. The lane rule limits what can be asked, not who asks. Recorded in the runbook and in the proposed risk.
6. **Data.** Briefs and reports written by agents. No learner data. They are kept until someone deletes them, and the tool never deletes.
7. **Risks (proposal; principal-engineer-ops writes the register).** New: "mailbox sender is unauthenticated: an agent can write a dispatch-request as its manager". Likelihood 2, impact 2. The mitigation is that the chief of staff starts every run, and the event log records the chooser. It re-scores to closed if the hook stamps the sending agent's role into the message (a later change).

- **§7 risk, the unauthenticated `--from`: accepted for the pilot, re-scored.** I read the impact as **3, not 2**. A worker that sends as evaluation-steward can ask lane 10 for a checker with a brief it wrote itself. That breaks "evaluators see the artifact before the account" (CLAUDE.md). A gate that was not independent can then let a defect through to a published lesson. Likelihood stays at 2: only agents write the spool, the chief of staff starts every run, and the claim marker plus the event log record who started it. That gives L2 × I3 = 6. The risk is acceptable for a 3-day pilot on one lane (verticals) and not beyond it.
- **Conditions:**

  3. **The dispatch-check step is mandatory.** Failure (b) in §1, the double start, is safe only if dispatch-check runs before every start. The chief of staff's drain must never start a run whose `dispatch-check --source=mail:<id>` did not PASS. A run started without that check is a SEV3, which I declare.
  4. **Risk registration (proposed id R-030)** is blocked by the same thing as F-39's risk: an `open` risk needs a board id, and this slot cannot write board.json. The chief of staff adds "Stamp the mailbox sender's role (F-42 --from)", owner tools-lead.
