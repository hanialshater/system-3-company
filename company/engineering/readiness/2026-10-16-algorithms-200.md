## The check

1. **What can fail.**
   - **A model or initial frame teaches the wrong mechanism.** Learners see this only if a lesson is later promoted with a wrong claim. All 200 lessons are draft and 4,407/4,407 claims are unverified, so the fact-check (W-1628, batches of 30 or fewer) and the learner sample (W-1629) stand between them and learners.
   - **An engine bug breaks all 200 at once** (`AlgorithmLesson.tsx`, `AlgorithmState.ts`; the R-019 pattern). Reveal could unlock early, the Seen proof could be lost, or a control could do nothing. One case already happened: 5 lessons had a "Try another" that changed nothing (M3).
   - **Worst: the catalog.** `src/app/catalog/page.tsx` is live public surface and ships at the next deploy, whatever the lessons' status. A mistake there would list the 200 unreleased draft titles on the production map, and 120 of them are unclaimed declarative sentences. Every visitor to /catalog would see it.
2. **How we would know.**
   - **Engine and specs:** `npm run test:algorithms` runs in `verify` (417 tests). It covers the transition model, `checkAlgorithms()` on the real manifest, exact wrapper imports, and that case 1's visible frame differs from case 0's. The QA contract checks dead controls, locked predict and reveal gating, and it runs in CI's `npm run qa`.
   - **Catalog:** `tests/algorithms/catalog.test.mjs` renders the real page under `VERCEL_ENV=production` with all 200 lessons draft. It asserts that the section is absent, that none of the 200 names appear, and that no "planned" copy appears. The map test in `tests/qa/feed.spec.ts` also runs in CI.
   - **Gap:** only the 4 built-output tests (W-945/946/947) would catch drafts leaking into the production prerender or client chunks. They need a `VERCEL=1` build and did not run on this head. They should run on the build that is deployed, before the first deploy that includes this merge (release manager; the same condition as W-1513 for Books).
3. **How to roll back.**
   - **Before a deploy:** the path-limited restore under "Final commit list" (prescribed; it keeps the records), or `git revert -m 1 <merge of PR #6 into base>` if losing the paper trail is acceptable. Then run `npm run registry`, `npm run check`, typecheck, the build and the affected QA: about 10 minutes plus a build.
   - **Revert as one group:** the engine, its 200 consumers, the catalog section, `test:algorithms` and the records. Do not revert the engine alone, because 200 wrappers import it.
   - **After a deploy:** a Vercel rollback to the previous production deployment (company/ops/runbook-deploy.md), then the restore.
   - **Data and approval:** no learner data, migration or external resource exists, so nothing is lost. The revert needs no founder approval; any redeploy does.
4. **Capacity.** Measured in M5 and the contract run, on the shared 4-CPU host (R-001).
   - **Build:** 191 s wall (Turbopack, one build at a time; 138 s under lower load). PR #5 took 116 s. 2,627 static pages.
   - **Output:** `.next` is 610 MB (PR #5: 570 MB). `static/chunks` is 42 MB on disk (PR #5: 33 MB). The per-chunk ceiling (W-946) was not checked.
   - **Full QA:** 2,560 tests in 4,708 s (1.3 h) at 2 workers. The 200 new lessons add 400 contract tests, about 8 minutes at 3 workers, to every full `npm run qa` in CI (R-002).
   - **Source:** `src/lib/algorithms` is 380 KB and `src/components/algorithms` 20 KB. Each wrapper imports one topic module (10 specs), not all 200, so a lesson page loads one module.
   - **Vercel quota and usage budget:** this merge requests no deploy.
5. **Security.**
   - Neither the engine nor the catalog change adds a route, API, query parameter, iframe, third-party script, secret, permission, `fetch`, storage, `eval` or HTML injection.
   - `tools/serve.sh` now binds `next start` to 127.0.0.1, which narrows exposure. The review accepted it; a lane that needs remote access asks tools-lead for an explicit opt-in.
   - Production visibility is unchanged. Since base `af8e4021`, the PR side changes none of `src/lib/visibility.ts`, `src/lib/catalog.ts`, `src/kit`, `src/app/d`, `next.config.*`, `vercel.json` or `tsconfig.json`. Drafts stay unreachable by URL on production (test:platform #29 passes), and the catalog section reads only `visibleDemos()`.
   - Not verified on this head: the built-output check that no draft text reaches client chunks (see check 2).
6. **Data.**
   - The change writes nothing new. Model cases are finite in-memory inputs. Existing kit progress and events are unchanged, and there is no learner identifier.
   - `tools/materialize-algorithms-200.mjs` writes only new lesson directories and refuses existing ones. It is a builder tool; the app never runs it.
   - No privacy review is needed.
7. **Risks.** No new entry is proposed.
   - **R-019** (shared lesson engines fail many lessons at once) now covers a fifth engine. This change brings its own mitigation: test:algorithms in verify, the shipped-spec test, and contract QA on all 200.
   - **R-001 and R-002:** about +40 s per build and +8 min per full QA run (check 4).
