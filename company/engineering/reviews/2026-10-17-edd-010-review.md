## 1. Findings (problems, not fixes)

**F1. The candidate imported from `company/` into a client bundle (§5.1 row 1).** It is technically possible: Turbopack's root is the checkout (next.config.mjs), and tsconfig already includes `**/*.ts`. But it carries three costs. (a) paths.json classes `company/**` as tier 0 ("records and docs"), so an edit to a file that ships to every learner would classify as tier 0. (b) It would be the first client-bundle import from the handbook tree. The only existing `src` import from `company/` is a lesson's build-time `gen.mjs`, which is not bundled. `company/` is where internal strings live (W-946/W-947), and a precedent here lets one leak. (c) T5 as written hashes a path, not "the file the glue imports". **Ruling: use the byte copy** at `src/lib/learner/reachable-v2.ts` (the EDD's own fallback). T5 then hashes both files to the frozen hash and parses the glue's import specifier (C1). The hash test makes the copy unable to drift, so "nothing can drift" still holds. The original stays frozen and unedited.

**F2. `src/lib/learner/**` has no paths.json rule, so it classifies as tier 1** (default 1; checked in paths.json). The EDD's "tier 2" labels in §5.1 are not enforced by the readiness gate today. That is my file (C2).

**F3. One generated module for both dims and cards couples a tier-2 policy input to lesson churn.** `PILOT_CARDS` carries the claim counts (`trustCounts`), titles and hooks. Every fact-check verification in a pilot lesson changes a count (72 claims are waiting today, per `company status`). So a tier-0 lesson edit would either force a regeneration of a tier-2 file, or leave a bundled card whose "x/y claims checked" disagrees with its `/api/feed` copy. That count is a learner-visible fact. The registry already solves this pattern: `npm run build` runs `registry` first. **Split the module** (C3).

**F4. "Pilot slot" is defined by domain, not by membership in `PILOT_DIMS`** (§5.4 step 3, "D[i] is a pilot lesson"). On a dev or local build `visibleDemos` can differ, and a lesson published after the generator last ran can be in `D` but not in dims. With a domain test, such a slot is refilled from `R`, its own lesson is lost, and `R` runs short. The same shortfall happens if a completion is written in another tab mid-session: `R` drops the slug, but no pin keeps it. The §5.4 "R runs out" fallback catches it, but T8 asserts that it never happens, so T8 would be wrong, not the code (C4).

**F5. Bundle size is an estimate in JSON bytes, not built bytes** (§3.4, §7). What ships is the minified TS module plus `rank` (512 source lines) plus the glue. The 300 KB cap is per chunk. Feed's chunk has room (18 KB today). But nothing fixes which chunk Turbopack puts the generated module in, and one learner chunk is already 230 KB raw, so the result depends on placement. Under my authority I require the measurement before the size claim is accepted (C5). Every visitor to `/` pays the gzip delta, including those who never reach a pilot slot. Record it.

**F6. "Compiled out when off" rests on tree-shaking that nobody has shown for this build.** Next inlines `NEXT_PUBLIC_*` at build, so the `if` folds. But a statically imported app module with no `sideEffects` declaration is kept or dropped at the bundler's discretion. T1(c)'s markers are also weak as written. If the glue imports only `rank`, the string `"reachable-v2"` (inside `REACHABLE_V2`) is shaken out even when the flag is on. And slugs are no use as markers, because DemoHost's loader map already ships them. The negative test needs a positive twin and sentinels that survive minification (C6).

**F7. Hydration and pins have three gaps.** The basic approach is right: transform in an effect after hydration, server HTML = default order (T10). The gaps:
- (a) **Scroll before hydration.** `active` starts at 0, and the IntersectionObserver effect sets it only after mount. On a slow phone the learner can be on card 3 when hydration happens. The reorder effect would then pin only items 0 to 1 and swap the card on screen. The initial `h` must come from the scroller's real position, not from `active`.
- (b) **Margin.** At threshold 0.6, when card N becomes active, card N+1 can be 40% visible, and during a fling or smooth `go()` scroll N+2 can show before `active` updates. "max active + 1" is too tight, and the EDD leaves inclusive vs exclusive undefined.
- (c) **Pinned reasons.** The EDD freezes the card before `h` but does not say its reason line is frozen too. A recompute changes `R`'s runs, so a visible line could change text.
- Also: (d) `h` is in "all"-feed positions. `chooseFilter` resets `active` to 0 and scrolls to top, so `h` must only move while the filter is "all". (e) `reactStrictMode: true` double-runs effects in dev, so pin updates must be idempotent.

**F8. The failure fallback breaks the pin invariant.** §5.4 "Failure" says: on throw or over-budget, "the feed shows `D` for that render and every later one". Mid-session, cards before `h` may be moved cards. Showing `D` swaps them on screen, which is exactly what G-8 and T9 forbid. T13 ("gives D") and T9 contradict each other. Two more problems with the time-based trigger. First, `rank` is synchronous, so the check runs after the slow call has already janked: it cannot save that frame, it only switches the feature off for the page's life. Second, one GC pause can do that, silently, for the heaviest users (150 completions measured 10.7 ms unthrottled; ×4 throttle puts the median near the 16 ms budget). Recomputing `rank` on every `active` change is also more work than needed. The history changes only at reveal or recall, so `rank` can be memoised on the history, while the cheap fill re-runs on every swipe (C8).

**F9. Float ties across engines (engineering input to Q-R1).** `rank` breaks ties and picks `default-order` with exact `===` on values built from `Math.exp`, `Math.log` and `Math.pow`. ECMAScript leaves those "implementation-approximated", so V8 (Node, where every test and probe runs; Chromium) and JavaScriptCore (every iOS browser) can differ in the last bits. Within one engine, ties between identically computed values stay exact. The risk is two values that are mathematically equal but computed in a different order (for example a product over prerequisites listed in a different order), or distinct values a few ulps apart. Their order, and so §6.3's run boundaries and reason codes, could differ between iPhone and the tested engine. A 1-ulp gap would also count as a "real" reason under F6's T0 (`value(u) > value(l)`). Nobody has counted how often this happens. It may be zero (C9).

**F10. T6 cannot run in `npm run check` as written while reason copy is empty.** "The flag cannot be on while `reason-copy.ts` is empty (T6 fails)." If T6 runs in check unconditionally, it fails today, and that blocks the flag-off merge the EDD itself plans (§9.1). The completeness half has to be enforced where the flag is on, which is the build (C7 and C10).

**F11. Some tests the EDD places in verify never reach CI.** CI's verify job runs check, typecheck, build and qa, never the `test:*` scripts (.github/workflows/ci.yml; my W-1716 review). So T1(c), T10 and T11 in `tests/platform/` run only on a local `npm run verify`. That is the fourth suite with this gap. I am not asking for a ci.yml amendment inside this change. I am asking that the merge record and the release record paste the verify summary (C10).

**F12. Items missing from the file table.** §5.3's build log line `new-lesson-order: on|off` needs a next.config.mjs change (tier 2, build class), and §5.1 does not list it. The deploy pin (Q-O1) is W-1783 (release-manager with platform-engineer). It gates flag-on, not merge.

**What is right and should not change:** one code path. There is no cold-start wrapper (batch 5 §14.1). `D` is never mutated, so `chooseFilter`'s seeding and page merges keep their properties. No new request, key or log. Length-preserving, so revisits land where they do today. The flag value names the candidate. Option A over C and D. E is kept as the fallback if C5 fails.

## 2. Cold start and reason lines: the engineering side only

- **Cold start (O-S1, decided by vp-personalization in §14.1).** Engineering has no objection to `rank`'s own empty-history order. It keeps one path, and a wrapper would be policy in glue. Consequences to build for:
  - Cold start is the most common state: every new device and every cleared storage. 229 of 230 pilot cards are "moved" there, so the reason-line path and the DemoCard reason layout run on almost every pilot card of every first visit. P2 has to be checked at cold start, not only with a history.
  - The cold-start display uses no learner data and no clock. In rank.ts, `kNew` and `refreshPrior` do not read `now`. So a test should assert that it is identical for any `now` and any device: T12 plus a two-`now` assertion.
  - G11 and MR line 17 (intro copy, W-1764, W-1781/W-1782) gate **flag-on**, not the flag-off merge. The intro copy lives in Feed.tsx's `IntroCard`, so a copy change there is a platform-engineer surface change and is read against `tests/qa/feed.spec.ts` (protected). Not this change.
- **Reason lines (Q-R1 is with learning-scientist-personalization, F6, W-1785, in progress).** I rule nothing on truth. The engineering side:
  - §6.3's rule must be a pure function of `rank`'s output, in the glue, with the same `===` run test `rank` uses. It is table-tested against the probe vectors, and the candidate is untouched.
  - The set of keys it can emit is fixed: {earlier, later} × {prerequisites, concept-known, domain-estimate, refresh}. `reason-copy.ts` is checked against that set.
  - F9's near-tie count goes to F6 as an input.
  - If F6 forces a v3 that emits moving reasons itself, the glue's §6.3 function is deleted, not adapted. The v3 needs its own review (G6).

## 3. Decision

**Approve with conditions.** The architecture is sound and the simplest one that keeps `rank`'s semantics with no new request: a client view transform over an unmutated server order, behind a build-time constant. F7 and F8 are real defects, but they are fixable inside this design, so I do not reject it. **Merge with the flag off** is allowed when C1 to C8, C10, C11 and C12 hold, plus platform-engineer's sign-off (§4). C9 and every gate in EDD §10 and batch 5 §12 (W-1764, W-1765, W-1766, F6 and RC, K6 and G, W-1783) gate **flag-on**, and this review clears none of them.

Objections that travel with the decision:
- **D1 (mine): the per-call time budget as a kill switch.** I would rather have no runtime time trip at all, and enforce the budget with C8's bench before release, because a post-hoc trip cannot save the slow call. C8 lets the author keep a trip if it uses the pin-safe path and needs more than one slow call. The author decides and writes the answer in the EDD.
- **D2 (mine): F1's ruling reverses the EDD's first choice.** The author may contest it in an EDD addendum. The bar is a reason why an import from `company/` is safer than a hash-locked copy, given paths.json and W-946.
- **D3: no ADR.** The flag mechanism is reversible by one build, and the copy-plus-hash pattern is the one already ruled for T5. If a second candidate or second flag appears (v3 under G6), I write an ADR for "learner-policy modules: placement, hash lock, build flag".
