## Findings (problems, not fixes)

### F1. Path map: mostly right, with four errors
- **Dead glob.** `tools/registry*` matches nothing. The registry is generated by `tools/company.mjs registry`, and that file is protected, so it is already tier 2 through protected paths.
- **Missing: protected paths themselves.** README tier 2 includes "protected paths", but the map does not list them. The tool should read `protected-paths.txt` and not copy it, so the two cannot drift.
- **Missing: the lesson runtime and config that bypass the gate.** `src/app/d/**` (every lesson renders through it), `src/components/DemoHost.tsx` (loads every lesson), `src/app/layout.tsx`, `tsconfig.json`, `.vercelignore`, `playwright.config.ts` (can weaken QA without touching `tests/qa/**`), `.claude/settings*.json` and `.claude/hooks/**` (permissions for every agent). The gate's own files (`tools/readiness.mjs`, `paths.json`) were also missing. Without them, someone can switch the gate off as a tier-1 change.
- **No precedence, no tier 0, no default.** `src/**/db*` would match a lesson file named `dbscan`, and lessons are tier 0. The EDD does not say what happens to a path the map does not name. The map I confirm is ordered, and the first match wins. Protected paths come first, then the gate files, then the explicit tier-0 roots (`src/demos/**`, including the generated registry that every lesson changes, `content/**`, `company/**`, generated agents, root `*.md`), then tier 2. **Unmatched paths are tier 1**, so a new directory fails closed at the cheap tier.
- **The W-477 hole is not closed by paths alone.** `/spike` was a new `src/app/**/page.tsx`, and edits to `src/app/**` are tier 1. So a file the diff *adds* under `src/app/**/page.tsx` or `route.ts` is tier 2, because it is new public surface.
- **The "stricter wins" service-tier rule in the template cannot be checked.** `tiers.json` services have no paths, and `feed-and-lesson-runtime` is T1, which would make all of the feed UI tier 2. README says feed UI is tier 1. The path map is the single answer, and the template should say so.
- Map location (the EDD's open question): **data**, in `company/engineering/readiness/paths.json`. I wrote it with this review. README links to it. Nothing generates the table: one source and no generator to maintain.

### F2. Scaling: tier 0 is clean, tier 1 burdens the deploy
- Tier 0 is ignored, dispatch O1 fires only on tier 2, and tier 1 needs no person. That is right.
- **Tier 1 at the deploy is not right.** `--base` is the last production deploy. Every tier-1 change in between (HQ alone had 26 commits this week) then needs a self-check record, or the founder's approved deploy refuses. That is a tier-1 paper trail blocking a release over trivia. Tier-1 gaps should be **reported and logged** in the deployment record, and only tier-2 gaps should refuse. This still meets Amendment 1, which asks that a tool "look for" tier-1 and tier-2 records. The tool looks for them, and only approval blocks.

### F3. Stale records cover new changes for ever
A record covers a path if its `paths:` globs match and it was "committed at or before head". An approved record for `src/kit/**` from October would then cover every kit change after it, and one blanket record would empty the gate. A record must cover a path **only if it, or its `approved:` line, was committed in `base..head`**.

### F4. The first base does not exist
`company/ops/deployments/` holds only a README, so there is no production record, and `--base` is undefined. If it falls back to the root, the first strict deploy fails on all of history. A `since` commit is needed (set at the end of rollout week 1), and the base is the later of that commit and the last production record.

### F5. Enforcement: right for now, with three holes to name
- deploy.mjs plus O1, with no amendment, is the right first step. B repeats R-016, and C gates nothing while R-002 and R-003 are open. This is enough **as an advisory gate with an audit**. It is not "enforced" until W-480 closes the Vercel git path. Until then, no status line should say "enforced".
- **The call can be deleted.** `deploy.mjs` is not protected, and a change that removes the call is not checked by the call. Mitigation: the deployment JSON records the readiness result (pass, fail, override, the uncovered list and the base). `readiness.mjs audit` lists every production record that lacks the field, or fails it. The audit is the EDD's own measurement, and it should run in the ops review. A missing field is then visible after the fact.
- **The override is a free string.** `--override=<decision record>` must name an existing file under `company/decisions/` whose header says `owner: founder`, or the tool refuses.
- **Identity is testimony.** `approved-by:` is text that any agent can type. That is the same limit as every record here. The git trail (who added the line, and in which commit) is the evidence. I accept this and do not add a check for it now.
- **Promotion: only after W-480.** Then decide (with W-479 and AMD-003) whether `vercel.json`, `deploy.yml` and `deploy.mjs` become protected.

### F6. Fit with the engineering review: two forms for tier 2
For a tier-2 change, the engineer would write an EDD (which has rollback and measurements), then a readiness record with seven sections, and then the eng review asks about rollback and security again. That is two forms with overlapping questions.
- **Merge:** the engineer answers the seven questions **once, in the EDD**, in a new "Operational readiness" section of the EDD template. The tier-2 readiness record is then only the machine header, `links:` to that EDD section, and principal-engineer-ops' approval block. The eng review checks that the record is approved and reads rollback and security from the same EDD section. It does not ask them again.
- The two signatures stay separate: the eng review by principal-engineer, readiness by principal-engineer-ops. They are different reviewers' outputs, not the engineer's forms. principal-engineer-ops attends the eng review for deploy, event-API, auth and data changes, so both can be signed the same day.
- Tier 1 keeps the short self-check record. A tier-1 change has no EDD, so it has nothing to merge with.

## Decision

**Approve with changes.** Status set to `approved with changes`, indexed in `company/engineering/README.md`. W-790 can start. The changes are conditions on the build, not a redesign.

- **C1 (done in this commit; principal-engineer).** The confirmed map in `company/engineering/readiness/paths.json`, with ordered rules, protected paths first, explicit tier 0, default tier 1 and the added-route rule (F1). README's tier section points to it.
- **C2 (W-790; tools-lead).** Freshness (F3): a record covers only if it was committed, or approved, in `base..head`. Test: an old approved record plus a new kit change fails.
- **C3 (W-790; tools-lead).** The `since` floor (F4), and a report-only mode while `since` is null.
- **C4 (W-790; tools-lead).** At the deploy, tier-1 gaps WARN and are logged, and only tier-2 gaps refuse (F2).
- **C5 (W-790; tools-lead).** Deployment JSON gets a `readiness` field. `readiness.mjs audit` over `company/ops/deployments/` flags records with no field or a failing field (F5). The override must name a founder decision file.
- **C6 (done in this commit; principal-engineer).** The EDD template gains "Operational readiness", and the eng-review template checks the readiness record instead of re-asking (F6).
- **C7 (principal-engineer-ops).** In `ops-readiness.md`: replace "stricter wins" with "paths.json decides". A tier-2 record is the header, an EDD link and the approval. Remove "(review pending: EDD-007)".

Objections that travel with it:
- *C4 weakens the founder's ask for tier 1.* What happened: the tool still looks for tier-1 records and logs each gap in the deployment record, and the ops review sees them. Only the refusal is held back, because a missing self-check on HQ CSS should not block a release the founder approved. If tier-1 gaps in the audit are over 1 in 5 changes after two weeks, principal-engineer-ops can ask to make them refuse.
- *Tier 2 on lifehacks engines will be the main approval load* (21 commits this week). What happened: it stays tier 2, because one wrong spec reaches 120 lesson files. The EDD's delegation clause (median approval over 4 h for a week) is the relief valve.
- *Advisory until W-480* (EDD's own). Stated in F5. It is not hidden, and not called enforced.
