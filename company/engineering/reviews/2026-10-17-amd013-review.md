## 3. Findings

**F1 (blocking): the hold floor depends on the lib.** The ratified text, part (a) 2, says: "An active-hold floor
that does not depend on the lib. The hold file is read in `company.mjs` too." The protected diff imports `loadHolds`
from `tools/lib/readiness.mjs` and builds the floor from it. I tested a one-line lib edit, `loadHolds` returning
`{}`. The canary still passes, because it injects `hold` straight into ctx. `company status` then listed 38 lessons
as ready, 37 of them held (Life Hacks and History incubation, W-513 and others), and `company publish` would pass
them. This is exactly the bypass the floor exists to stop, and the protection would not notice it.

**F2 (blocking): the lib can drop the protected strictness parameter without tripping anything.** The text says
"the strictness parameters stay in company.mjs". But every canary case runs with `versionSince` unset. I tested a lib
edit that ignores `ctx.versionSince`. It passes the canary, and `check` passes. That edit voids `READINESS_SINCE`,
the one parameter that makes every future QA record carry its version. The same gap will open for `recorder` when
`QA_INDEPENDENT_SINCE` is set.

**F3 (blocking for the apply, not a code defect): A2's literal date fails 3 published lessons.** All 3 were
published before `c31c1fab` and pass with `null`. The cause is that their newest QA records are dated 2026-10-17,
and the stamp does not exist yet. Two of them are hand-written records that do carry the version, but in the form
`lesson version: 3` / `lesson version: 2`, without the `v`. `QA_VERSION` requires `v(\d+)`.
`left-or-right/2026-10-17-qa-v3.md` carries no stamp at all ("meta.version 3" appears only in its title).
Any QA record that the unpatched `qa-record` files today, before the apply commit lands, will fail the same way.
A3 forbids grandfathering them silently, so check would stay red and A4 cannot go green.

**F4 (blocking for part b): `ci.yml` lists 11 suites, and `verify` now runs 12.** Analytics added `test:metrics` to
`scripts.verify` after `c31c1fab`, between `test:memory` and `check`. The ratified intent is "the harness Node suites
that `verify` runs, in verify's order", so the list as drafted is now short by one. `test:rituals` is not in
`package.json` at HEAD, so it must not be added yet: `npm run test:rituals` would fail the job. Every other name
matches `package.json` exactly.

**F5 (fails closed, but crashes): an unreadable hold file throws outside the try.** `readinessOpts()` calls
`loadHolds` before the `try` in `readinessGates`. A malformed `publish-holds.json` makes `status`, `publish` and
`check` exit with a stack trace. That fails closed, but it gives no gate message. C1 fixes it.

**F6 (non-blocking): a lib that fails to load takes down the whole CLI.** The static import means a syntax error
in the unprotected lib breaks every `company` command, including `board` and `qa-record`, not only the gates. That
is closed, but it is a wide blast radius for an ordinary-surface edit. A guarded dynamic import (top-level `await
import()` in try/catch, then `readinessGates` returning "readiness lib failed to load") would keep the board usable.

**F7 (non-blocking): the grandfather list is keyed by slug, not by slug and version.** A grandfathered lesson keeps
its exemption in `check` after it is bumped to a new version. This is not a publish hole: `company publish` always
runs the full `launchGates`, with no grandfathering. But a hand-edited re-publish of one of the 268 would stay
silent in `check` (O5). `"slug@version"` entries would close that, at no cost to day-one behaviour.

**F8 (non-blocking): CI's checkout is shallow (`actions/checkout@v4`, default depth 1).** `gitAncestry` returns
null for every SHA there. The result is identical today (measured), but `qaVersionProblem`'s signal 2 ("built
before the current version") abstains without history and falls back to dates. So CI can be more permissive than
a local run for a future lesson. Adding `fetch-depth: 0` to the verify job's checkout would close that.

**F9 (non-blocking): `publish-ready.mjs` lists candidates without `versionSince`.** Once `READINESS_SINCE` bites,
its list can include a lesson that `status` blocks. That is safe, because `--publish` shells out to
`company publish`, which re-gates. But the amendment's prediction "status lists exactly what publish-ready lists"
will drift, and the first launch review should expect that.

**F10 (note): companion test 8 becomes a tautology after apply.** `publish-ready.mjs` then re-exports the lib's
`decide`, so the test compares the lib with itself. It did its job, proving the move preserved behaviour, at
draft time. Keep it or drop it; it costs about 300 ms.

What is right, and worth keeping:
- `launchGates = claimGates + readinessGates`, with `claimGates` byte-identical to today's body.
- `status`, `publish` and `check` all call through it. `publish-ready --publish` lands on `company publish`.
- The `try` around `readiness(loadContext())`, plus the shape check on the answer.
- The canary is cached per process, uses synthetic records and needs no disk.
- `qa-record` stamps `lesson version: v<meta.version>`, which the lib's `QA_VERSION` reads.
- The `nowPass` warning gives the grandfather list a visible way to shrink.
- The QA rule's fail-closed choices: a same-day tie goes to the fail, and a newer linked unreadable record holds.

## 4. Conditions (all four before the A1 commit)

- **C1 (F1, F5): the hold floor reads the hold file in `company.mjs`, not through the lib.** Remove `loadHolds`
  from the `company.mjs` import. Add a local reader that returns `null` when the file is unreadable or not an
  object. Pass its map to the lib as `opts.holds`, so the lib and the floor read the same map. Make `readinessGates`
  return a closing gate when it is `null`. Prototype, tested in the throwaway copy:
  ```js
  function readHolds() {
    const p = rel("company/ops/publish-holds.json");
    if (!fs.existsSync(p)) return {};
    try { const h = JSON.parse(fs.readFileSync(p, "utf8")).holds ?? {}; return h && typeof h === "object" && !Array.isArray(h) ? h : null; }
    catch { return null; }
  }
  // readinessOpts: holds: readHolds()
  // readinessGates, after opts: if (!opts.holds) return ["company/ops/publish-holds.json is unreadable; every gate is closed until it parses (AMD-013 hold floor)"];
  ```
  Result: with the `loadHolds -> {}` mutant, status lists only `zero-loses-to-this-crowd`, and a malformed hold
  file closes every gate with that message. Also add a companion test for the `loadHolds` mutant next to tests 11
  and 12.
- **C2 (F2): add an 8th canary case for `READINESS_SINCE`.** The case is a launch at the current version plus an
  unstamped QA pass dated on or after a synthetic `versionSince`, and it expects not ready:
  `["unstamped QA on or after READINESS_SINCE", { learner: [learner("launch", 2)], qa: [{ f: "2026-01-02-qa.md", t: "date: 2026-01-02 · result: **pass**\n", linked: true }], hold: null, versionSince: "2026-01-01" }, false]`.
  Tested: the ignore-`versionSince` mutant now trips the canary, and all 30 publish tests still pass. Whoever
  applies AMD-010 part 3 adds the matching recorder case when `QA_INDEPENDENT_SINCE` is set. O4 already gives the
  board this power, so adding a case is within the ratified text.
- **C3 (F3): make check green at the literal A2 date without growing the grandfather list.** Do two things before
  the A1 commit:
  - (a) Loosen the lib's `QA_VERSION` to `/lesson version:[ \t]*v?(\d+)\b/gi`. This is an ordinary-surface tune,
    and it accepts the hand-written form. Measured: it clears `draw-a-table-knot` and `tricolour-check`, and it
    lets 3 grandfathered lessons pass (`price-tag-or-auction`, `same-picture-two-histories`, `worth-something-alone`).
  - (b) qa-tester re-files a stamped QA record for `left-or-right` (v3), and for any lesson that gets an unstamped
    QA record later today.
  If the founder prefers not to wait, the only other honest path is a recorded founder decision that sets
  `READINESS_SINCE` to `"2026-10-18"`. That departs from A2's wording, and A2 is ratified text, so it is the
  founder's call, not mine. Either way, the applier re-runs `check` with the final value on the applying parent.
  `measure.mjs` alone is not enough, because it models `null`.
- **C4 (F4): add `- run: npm run test:metrics` after `test:memory` in the `ci.yml` hunk, and update the comment to
  "12 suites".** Do not add `test:rituals` until the held tier-2 commit puts it in `package.json` and `verify`. When
  that lands, its own amendment adds the line, because `ci.yml` is protected.

Recommended, not conditions: F6 (guarded dynamic import), F7 (`slug@version` grandfather entries), F8
(`fetch-depth: 0`). F7 and F8 are cheapest to do in this same commit, because both touch protected text that would
otherwise need another amendment later. Longer term, a drift test (ordinary surface) that asserts `ci.yml`'s
`test:*` steps equal `scripts.verify`'s would stop F4 from recurring silently.

## 5. Part (b) cost

The suites take about 53 s locally (1,366 tests), 20 s of it dispatch. Expect roughly 1 to 2 minutes on
`ubuntu-latest`. That is well inside the amendment's own "would be wrong if CI grows by more than 3 minutes"
bound. Running them before `check` and the build fails fast, which is correct. The `concurrency` block is untouched.

None from me against the policy. O1 (the judge sits in an unprotected lib) is the same class as F1 and F2: C1 and
C2 shrink it, but they do not close it. A1 (protect the lib) remains the full close, and that is the board's call.
