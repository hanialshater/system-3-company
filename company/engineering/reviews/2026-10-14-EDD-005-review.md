## Findings (problems, not fixes)

### 1. Correctness: decided once, before first paint, before the W-287 fit. Holds.
- **Once.** `onChange` returns at `isReveal === revealed`. `decideFold` runs only on the false -> true edge. Its own `flushSync` renders add a toggle node (a childList mutation), so the observer fires again, and that call returns at the guard. The 400 ms timer, the ResizeObserver, `orientationchange` and the toggle's own resize all go through `bringIntoView`, which never calls `decideFold`. So re-fits can never fold or unfold (spec item 3).
- **Before paint.** MutationObserver callbacks are microtasks. React 19 commits sync-lane work in a task or in its own microtask, and the observer record is queued during that commit, so the callback runs after the commit and before the next rendering step. Both `flushSync` renders (fold, and the undo if it does not pay) and both layout reads happen inside that callback.
- **Before the picture fit.** `decideFold` runs in the callback. `scaleStage` runs later, in `requestAnimationFrame(bringIntoView)`. Pictures are at natural size when the fold is decided: `unscale` runs when the phase leaves the reveal, and `scaleStage` measures again from natural size on the folded layout.
- **The flagged risk (flushSync from an observer microtask) is low. I accept it.** In React 19.2.0, `flushSync` warns only when `Internals.d.f()` reports that React is already rendering or committing. A microtask cannot run inside React's synchronous render or commit. React's own warning text says to use "a scheduler task or micro task", which is what this code does. The EDD's fallback (a `useLayoutEffect` in a kit component) stays the plan if a future React changes this.
- **Residual 1 (safe direction).** A lesson that commits `data-phase="reveal"` in one commit and the reveal's content in a later one (Suspense, lazy, an effect that sets the text) gets its fold decided against a short reveal, so it may under-fold. It can never fold late. I accept this, since the spec chose "once" over "right later".
- **Residual 2 (detection gap).** If React ever warns, the contract's "no page or console errors" check would catch it, but only on a lesson that actually folds on the contract phone. Today no lesson folds anywhere. Even the author's opted-in natural-selection fitted on Pixel 7 and returned before `flushSync` (EDD, Results). **The `flushSync`-from-observer path has never run under any automated check.** See change C1.

### 2. Interaction with W-287. Correct, with one stale-state case.
- Measuring stage height is valid: at the reveal, `.stage` is `flex: none; overflow: visible` (globals.css, `.lesson[data-phase="reveal"] .stage`). `.row` margins sit inside a flex column, so they do not collapse. Before minus after is therefore exactly the row heights plus margins, minus the toggle and its margin.
- The picture fit's candidate filter is not affected by the toggle, which contains no svg. Its overflow reading is taken on the folded layout, so pictures shrink less, as the spec intends.
- **Stale state after a press (accepted, note for W-351).** Any toggle press sets `touched`, and `bringIntoView` then returns for the rest of the reveal phase, rotation included. A learner who presses the toggle and then rotates keeps the picture `max-height` px from the portrait fit. That is what item 6 asks for ("the fit does not re-run"), but the cost should be known.
- **Design question, not a defect (travels as objection O1).** Item 2 folds whenever `over > 1` and the fold pays. A lesson that is 3 px over, which the picture shrink would absorb above the 10 px floor, will still hide controls. The fold-first order is in the spec. Whether a small overflow should go to the picture shrink first is a design-lead call.

### 3. Focus handling. Mostly right, two small defects.
- Right: `hadFocus` is read before the fold render, so the browser's focus fixup cannot hide it. The toggle gets `focus({preventScroll: true})` only if focus was inside a folded row. The click handler focuses the toggle explicitly (Safari). Tab order is DOM order, because the toggle renders as a sibling just before the first folded row.
- **D1. The fallback `lastFocus` is never cleared.** It holds the last `focusin` target in the card body, however old. If the learner used a slider in an opted row and then moved focus to `<body>` some other way (for example, by tapping a non-focusable part of the stage), the fold still moves focus to the toggle. That programmatic focus makes a screen reader announce the toggle over the reveal, which is the announcement item 5 avoids. The fallback is meant only for the case the author found: focus lost because the reveal commit disabled the focused control.
- **D2. `scrollParent` can escape the card.** When the fold closes the overflow, `.card-body` stops overflowing, and `scrollParent(btn)` walks up to `.feed` (`overflow-y: scroll`, `scroll-snap-type: y mandatory`). A non-zero `moved` would then scroll the feed off its snap point. With rows opening below the toggle, `moved` is about 0, so this is unlikely. Bounding the walk at the card costs one line.
- Physics, not a defect: on Hide, if the scroll range shrinks below the current `scrollTop`, the browser clamps it and the toggle cannot keep its position. Item 5 asks for position keeping on expand only.

### 4. Net-saving threshold. Matches the spec.
- Code: keep the fold if `saved >= max(44, toggle border-box height)`, where `saved` = stage height before minus after, with the toggle and its 8 px margin already inside "after". That is spec item 2 word for word: rows plus margins, minus toggle plus margin, at least the toggle's height. The first-build error (52 px bar) was caught and corrected by the author's own test.
- **For W-333 (so the tool and the kit charge the same).** With today's toggle (44 px plus 8 px margin), the opted rows must total at least **96 px including their margins** to fold. reveal-fit's simulation should use the measured toggle height when one exists, not a constant.
- Note for W-333: `data-fold-refused` is written only when the card overflows (it comes after the `over <= 1` return). reveal-fit cannot read refusals on lessons that fit, and must compute the Readout and svg exclusions itself if it wants them everywhere.

### 5. QA contract. display:none only; the toggle is never pressed. Holds.
- Hiding: a folded row keeps its element and its children (never unmounted), and gets `hidden` plus inline `display: none` (needed because `.row { display: flex }` beats `[hidden]`). Nothing uses height, opacity, transform or visibility. The toggle's chevron rotation is decoration on the toggle, not a hiding method. This satisfies item 6.
- I read `tests/qa/contract.spec.ts` (unchanged by the commit). Step 3 presses controls before the reveal, when no toggle exists. After the reveal it only measures horizontal overflow and tap targets, with an `offsetParent !== null` filter, so folded controls are skipped. The toggle is at least 44 px, full width and border-box. **The contract never presses the toggle**, so the expand path stays uncovered until W-334 (evaluation steward) or W-333's expand check. Not my call; I am a reader here.
- `src/kit/Lesson.tsx` and `tests/qa/**` are untouched (item 8).

## Decision

**Approve with changes.** It stays merged and ships dark. Nothing here justifies a revert: no lesson opts in, the non-opted DOM is unchanged, and the open risk is retired by the React source. The changes gate the **first opt-in**, not the merge.

- **C1 (gates the first opt-in, W-441).** Run the folded state under an automated check with console-error capture: the toggle present at the first frame, no `flushSync` warning, rows `display: none`, expand and hide. It should live in W-333's reveal-fit expand check, on a lesson that actually folds at 390x844. Owner: platform-engineer.
- **C2 (small, before the first opt-in, W-442).** D1: use `lastFocus` only when focus was lost by the reveal commit, that is when `lastFocus` is now `:disabled` or disconnected; otherwise do not move focus. D2: bound `scrollParent` at the card body. Owner: platform-engineer. Tier 1, no further engineering review; W-336 (accessibility) sees the focus result.
