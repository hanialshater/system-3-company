## Findings (problems, not fixes)

### 1. Kit change: correct for the path it was built for
- **QA path holds.** The contract re-queries `[data-qa=control]` across the whole stage, hidden sub-cards included, presses index i only if it is visible and enabled, and caps at 16. The order is trail (n), card 1 controls, Next, card 2 controls, Next, and so on. All trail steps are disabled when QA reaches them: the current step is disabled, and so are unvisited steps. Pressing Next shows the next card before QA's index arrives at that card's controls. Enabling trail steps later changes their state but not their count, so indices never shift. Next changes `innerText` (the hidden card drops out), so it is never a "dead" control. Step 2 of the contract ("every control locked before the prediction") covers hidden controls too, because `toBeDisabled` reads the attribute. The trail and Next take `locked`, and builder controls must do the same, as they do today.
- **Milestones.** `reach` is namespaced, counts once, ignores names not declared and does nothing while locked. It is the only caller of `interact()`. Calls after the reveal are harmless, because `Lesson` reads `interactions` only while the phase is explore.
- **Reveal card before first paint.** The `setActive` in `useLayoutEffect` is a synchronous re-render inside the same commit, before paint. It also lands before EDD-005's MutationObserver microtask, so `useRevealFit` measures the final card. **This path never runs under QA or in the author's probe.** The example's reveal card is the last card, which is also where the QA path ends, so `at === active`. The path runs only when a learner taps back to an earlier card and then presses the reveal button (the button is outside the stage). I have checked it only by reading the code. See C1.
- **Silent misuse.** (a) An unknown `revealCard` id gives `findIndex` -1, which is silently ignored. (b) A `<SubCard>` wrapped in a fragment or a custom component is dropped by the `c.type === SubCard` filter. The dev warning fires only if fewer than 2 cards remain. (c) A sub-card with no milestones shows as done (tick and trace) as soon as the prediction is made, because card 1 is visited from the start. See C2.
- **For the design review (W-583), not a defect.** In the example, `trace` and the reveal are live values of `k`, not values recorded when the milestone fired. A learner who reaches "2 to 13" and then taps back and picks "2, 3" gets a reveal and traces about 2, 3, while the question asked about 2 to 13. The trace and the reveal agree with each other, so the kit is consistent. Whether the reference should record the question's case is a lesson call.

### 2. Contract risk: no contract change, but the format now depends on four properties of the contract
- The format works because the contract (i) presses controls in DOM order, (ii) re-queries after each press, (iii) skips hidden and disabled controls, and (iv) caps at 16. None of these is written down as a guarantee. If the evaluation steward changes any of them (for example, failing on hidden controls, pressing twice, shuffling, or a different cap), every sequence lesson breaks at once. This is a dependency to record, not a defect. See C3.
- **Coverage gap, bigger than the EDD says (O4).** The contract measures horizontal overflow and tap targets only after the reveal, and only for elements with `offsetParent !== null`. So **sub-cards 1 to n-1 are never checked for overflow or tap size by CI**. Only the trail and the reveal card are. `tools/reveal-fit.mjs` also sees only the reveal state. A builder's card 1 that overflows at 390 px passes every gate. The EDD's open question 4 (trail and swipe are not pressed) is real, but this gap is the one that will ship defects. See C1.
- Budget: n + controls + (n - 1) <= 16 is right. If a lesson goes over, the reveal does not unlock and QA fails visibly. The failure is loud but confusing, and the dev-only warning softens that.

### 3. Accessibility (engineering reading; the accessibility reviewer still owns W-584)
- Right: native buttons; hidden cards are `display: none`, so they are out of Tab order and out of the accessibility tree; focus moves to the shown section (`tabIndex=-1`, named "Step k of n: title") after a button move, so focus never falls to `<body>`; the live region exists from the first render and speaks only after a swipe; reduced motion sets `animation: none`; no arrow keys that would fight sliders; `focus-visible` outline on the section.
- For W-584 to judge: (a) the current step is a *disabled* button with `aria-current="step"`, so screen readers read it as dimmed or unavailable, and it is skipped in Tab order; (b) `aria-roledescription="step"` on a `group`; (c) the trace and tick appear without an announcement; (d) the iOS Safari edge back-swipe against the right-swipe (real phone).
- Theme: the kit uses only theme variables (`--muted`, `--good`, `--domain`), and dark is the default `:root`. The unchecked theme is light, which is low risk.

### 4. Bundle size
- **This change costs about 3.4 KB gzipped (9.1 KB raw) of JS, plus a 3.2 KB CSS file.** In the author's build, the sequence kit and the Euclid demo are one module span in the home chunk (`2malunqo9t3ps.js`) and the catalog chunk (`3t841ac50j65a.js`). That is about 0.4% of the home chunk. I measured module spans in one build, not a before/after pair.
- **Pre-existing, outside this change (S1).** The home and catalog chunks are each 3.1 MB raw / 911 KB gz, and they contain demo code: the Euclid demo's own `exploreHint` string is in both. The build has only 23 JS chunks for 880 lessons. So the per-lesson `() => import(...)` in `registry.generated.ts` with `next/dynamic` in `DemoHost.tsx` is **not code-splitting**: every lesson's code ships on the first page. This is a scale-budget defect that grows with each lesson, and it is filed separately.
