## Findings: R2

Things that hold (no change needed):
- A forged review inside the author's own section, written as a `### Review (...)` subsection: not covered. Only
  `## ` headings start review sections.
- Case mismatch (`## Review (Evaluation-Steward, …)`, `Verdict: ACCEPT`): covered. That is correct, because role
  names are normalised both ways. Owner `Tools-Lead (author)` against reviewer `tools-lead (self)` is still refused.
- The owner named as a reviewer on a second `reviewers:` line: refused.
- `status: final` only in the body, `status: not final`, an empty `reviewers:`, or the incident id only in the body:
  not covered.
- `verdict: accept-with-changes`, `**accept**`, `- verdict: accept`, `> verdict: accept`: not covered ("no verdict"
  or "<word> by <role>"). That is fail-closed.
- CRLF files: not covered. That is fail-closed, though an author would find it confusing (see change 5).
- A reviewer listed twice is deduplicated to one, and that one accept covers the incident. The spec sets no minimum
  number of reviewers, so this follows the spec. Whether a SEV1/SEV2 COE needs two reviewers is the evaluation
  steward's call.

Required changes (each needs a test in tests/dispatch/r2-coe.test.mjs):
1. **Code fences are not ignored, so R2 can pass without a real accept.**
   - (a) A section whose first `verdict:` line is inside a fenced block (a reviewer quoting the template or an
     example) and whose real line says `verdict: revise` is **covered**. `reviewVerdicts` takes the first
     `^verdict:` match in the section.
   - (b) A `## Review (evaluation-steward, …)` heading with `verdict: accept` inside a fenced block in the author's
     section is **covered**, because `split(/^(?=##\s)/m)` does not know about fences.

   Fix: remove fenced blocks before splitting into sections and before matching verdicts. Also, if a review section
   has more than one `verdict:` line and they disagree, fail closed with the reason "conflicting verdicts by <role>".
2. **The owner check fails open.**
   - With no `owner:` line, condition 4 is skipped and the COE covers.
   - With two `owner:` lines, only the first is compared, so `owner: tools-lead` followed by
     `owner: evaluation-steward` (who is a reviewer) covers.

   Fix: require exactly one `owner:` value. A missing owner should give the reason "has no owner: line in its
   header", and the check should compare every owner value against the reviewers.
3. **`status:` is too loose.** `/^final\b/` matches `final-draft`, and `status: draft` followed by `status: final`
   counts as final. Fix: require exactly one `status:` value in the header, matching `/^final(\s|\(|$)/i`.
4. **A bad record blocks every kind of dispatch.** One unreadable entry in records/ (I tested a dangling symlink
   named `2026-10-14-coe-broken.md`) makes `statSync` throw. dispatch-check then exits 1 with a stack trace for
   `--kind=check` as well, which the spec says must only warn. Fix: wrap the `coeCoverage` call in try/catch, and
   skip unreadable files with a reason. A build or wave should FAIL R2 with "R2 could not read COE records: <msg>";
   check, ritual and incident should get the same text as a warning.

Recommended (not blocking):
5. Accept CRLF by splitting on `/\r?\n/`, or say "CRLF line endings" in the reason. Today the reason is "is not
   status: final", which sends the author to the wrong line.
6. **Residual risk (route to the evaluation steward; it cannot be fixed in the parser).** A reviewer's mark is text
   in a file the author can edit. Anyone who can write the file can append a later `## Review (<role>, <date>)` with
   `verdict: accept`, and under "last section counts" that overrides a real `revise`. They can also write a second
   COE file naming the same incident. The parser cannot tell who wrote a section, and every agent commits as the same
   git user. Possible mitigations, for the steward to choose from:
   - check reviewer names against the roster (`reviewers: none` with a `## Review (none, …)` currently covers);
   - have `company coe-review` write the review section and log a dispatch event that R2 cross-checks;
   - have CI flag commits that change a `## Review (<role>` section from a session that is not that role.

## Findings: W-783 tool stamps
- **Normal use works.**
  - The committed `tools/reveal-fit.mjs` runs.
  - An edited copy exits 3 with a clear message, and so does an untracked copy (`tools/rf2.mjs`). I tested both in
    a scratch clone, not the worktree.
  - `--allow-modified` runs and stamps `clean: false`.
  - No npm script or CI step calls reveal-fit. tools/sequence-probe.mjs only mentions it in a comment, so nothing
    automated breaks.
  - Outside git (for example a Vercel build), the stamp returns `error` and refuses. That is correct for a measuring
    tool.
7. **Bypass: the stamp covers only its own file.** Editing `tools/lib/tool-stamp.mjs` to return `clean: true` and
   then editing reveal-fit gives exit 0 and a clean stamp. Fix: stamp `[SELF, tools/lib/tool-stamp.mjs]` (and any
   other local imports).
8. **Bypass: a local commit is "clean".** Committing an edit on any branch gives `clean: true` with a real-looking
   `commit`. The stamp is still honest, because it names the commit. But a reader must check that `commit` is an
   ancestor of `origin/main`, or that its blobs equal main's. The amendment should say so, for qa-record too.
9. **Bypass: the QA stamp can be forged through the environment.** playwright.config.ts trusts any inherited
   `S3_QA_STAMP`, so `S3_QA_STAMP='{"clean":true,"commit":"<current>"}' npx playwright test` writes a forged stamp. A
   malformed value also crashes the config at load time with a JSON parse error. Fix:
   - inherit only inside Playwright workers (`process.env.TEST_WORKER_INDEX` is set), and recompute in the main
     process;
   - wrap the parse and fall back to recomputing.

   The amendment's step 2 (recompute the commit) does not catch this forgery, because a forged stamp can carry the
   current commit.
- **playwright.config.ts does not change test behaviour.**
  - The diff adds one import, a stamp computed once (a few git calls at config load), a warning, and
    `metadata: { qaStamp }`.
  - `testDir`, timeouts, projects, webServer and reporters are unchanged. `metadata` is report-only in Playwright.
  - `gitStamp` catches its own git failures, so QA_BASE_URL runs outside git still work.
  - The commit touches nothing under `tests/qa/**` (`git diff HEAD~1 HEAD --stat -- tests/qa` is empty). The
    playwright config is not on the protected list.
- **The amendment proposal** (company/constitution/amendments/proposed-qa-harness-stamp.md) is honest that the stamp
  alone stops nothing. Before it is drafted and numbered, it should add findings 8 and 9 to "would_be_wrong_if" and
  to the proposed change. That is the evaluation steward's work (W-785 lane), not mine.
