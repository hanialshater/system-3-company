## Rulings

### 1. Mount path: **`/api/account/settings`. The cookie is not widened.**

ADR-008 item 3 already says "our own account routes … under `/api/account/*`", and item 4 scopes the cookie to `Path=/api/account` so that P6.2 holds by construction. A learner's own settings are an account route. Option (a) is therefore what ADR-008 already prescribes, and it needs no ADR change. Cookie path matching is by prefix, so `/api/account/settings` receives the session. Option (b) would undo the one property ADR-008 chose the path for. It would also need a new privacy read and an ADR supersession, all to keep a URL nobody has shipped. Rejected. Doing nothing leaves a route that can only answer 401. Rejected.

Consequences, all in C1: the route file moves to `src/app/api/account/settings/route.ts`. It then falls under ADR-008 item 8 (when `ACCOUNTS_ENABLED` is off, every `/api/account/*` route is 404, which the handler already does). The namespace is backend-engineer's, who must acknowledge it and confirm that no catch-all on the accounts branch (`/api/account/[...]`) shadows it. Better Auth sits at `/api/account/auth/*`, so there is no collision there. privacy-reviewer's B2 sentence ("only `PUT /api/settings`") becomes "only `PUT /api/account/settings`". I read that as a wording change, not a new ruling. privacy-reviewer decides whether that is true.

### 2. Location of the server modules: **approve `src/lib/server/personalization/`.**

`src/lib/server/` is the home the accounts env contract already names (`db.ts`, `auth.ts`, `accounts-flag.ts`, `email.ts`: company/engineering/notes/2026-10-15-accounts-env-contract.md). Server-only learner-data code belongs beside them, not in the flat `src/lib/hq-*-server.ts` pattern (that is HQ's, which never serves learners). The split is right as written: a pure module, a store that is the only SQL writer, a handler that never throws, and the wiring. Scope of this approval: the settings modules only. It does **not** decide where model serving lives. That remains W-1919 O1 (company/engineering/reviews/2026-10-16-w1537-check-wiring.md, part 2), which needs its own EDD and ADR.

The tier map does not cover this folder: `company/engineering/readiness/paths.json` has no rule matching `src/lib/server/**`. Today a later edit to `settings-store.ts`, the only writer of a learner table, would classify as tier 1. That is my file to fix (C2).

Table name: **keep `settings`**. EDD-008 §6.1, the W-1942 schema and the privacy ruling all use it. Renaming would buy nothing, and every record would need editing. It does not clash with anything in `public`, and Better Auth's tables are prefixed `auth_`.

### 3. `package.json`: **approve as written (`test:settings`, in `verify`, not `check`), with a CI condition before wiring.**

Verify is the right home under the convention, and check is not an option today. The suite needs the TS loader, which needs `node_modules`. Check has to keep running without `npm ci` (W-1958 review, "Rejected").

But B2 (only one writer) and B4 (no body logging) are privacy conditions whose value is catching **other roles' later edits**. A test that runs only in `verify` is a habit, not a gate. CI runs check, typecheck, build and qa, never `test:*`. While nothing is wired and no table is applied, nothing can be harmed, so this does not block the merge. It blocks wiring (C6). What I want is the CI amendment already on the board (W-1116 for `test:platform`, W-409 for deploy/lifehacks/kit, evaluation-steward), extended to include `test:settings`, ideally as one step that runs the `test:*` suites after `npm ci`. Fallback if the amendment stalls: make the suite loader-free and put it in check, provided check stays under the 3 s budget from the W-1958 record (measured today: 1.4 s + about 1 s). That needs explicit `.ts` imports and `allowImportingTsExtensions` in tsconfig, which is a shared-config change, so the amendment is the cleaner route.

## Findings (problems, not fixes)

1. **The route as mounted can never authenticate** (ruling 1). This is the only blocking finding.
2. **Read-modify-write without a transaction** (`handleSettingsPut`: `store.get`, then `store.put`). Two concurrent PUTs from two devices lose one update. The case that matters is a `merge` racing a `set` to `false`: the merge read "on" and writes it back, so an explicit off is overwritten. D2 and G3 hold per request but not across a race. Likelihood is low (two devices, same account, within milliseconds). Impact is a privacy property, so it is not mine to waive (C7).
3. **Body size is checked after buffering when there is no `Content-Length`** (chunked request). `req.text()` reads up to the platform's limit before the 16 KB check runs. This is minor: the platform caps it, and the cost is memory, not data. It is not a condition. Fix it if the wiring change touches that block.
4. **No CI enforcement of B2 and B4** (ruling 3).
5. **Tier-map gap** for `src/lib/server/**` (ruling 2).

Not findings: the Origin check (`sameOriginWrite`) is sound with `SameSite=Lax`, because a browser cannot forge `Host` or `X-Forwarded-Host` cross-site. The catalog memo is published content, not learner data, and D2 is respected because the row is read on every request. The `unchanged` check correctly rewrites a row whose stale ids the learner's write drops.
