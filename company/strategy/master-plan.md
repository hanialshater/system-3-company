## One section per project

### 1. First Light
- **Goal:** the first public release: a real domain, accounts, progress that follows the learner, rule-based personalization, mastery and challenges, light social, a labelled ad slot, legal basics (company/initiatives/first-light/charter.md).
- **Owner:** head-of-strategic-initiatives. **Dates:** go/no-go 2026-11-23, launch 2026-11-30.
- **Budget:** tranche 1 is 6.59M tokens with F-43's conditions (company/ops/projects.json).
- **Next decision:** the founder's go/no-go; before it, the budget rulings and EXP-002 (company/rituals/records/2026-10-17-founder-digest.md).
- **Not doing:** scale to 100k, new categories outside the launch set.

### 2. Code DB on top of git
- **Goal:** keep the git repository as the source of truth and the audit trail, with a database-shaped layer on top that can query and serve millions of lessons, claims and events. Files-in-git do not hold that today: `check` reads every meta.json, and the build pre-renders every page.
- **Owner:** to be named (principal-engineer for the design, platform-engineer to build).
- **Starting point:** EDD-003 (lesson storage at scale), scale-stage-0 (SPIKE-001) and scale-stage-1 (the registry split and the 50-lesson runtime-bundle pilot).
- **Next decision:** the founder starts it; then an EDD that names the target (how many lessons, claims and events, read and write rates), and what stays in git.
- **Not doing:** moving off git as the record.

### 3. System 3 Meta
- **Goal:** the startup: an operating system for companies of fallible agents and people, on the philosophy of science and Amazon-style management, adapted where agents differ (company/sibling/system3-meta/founder-brief.md).
- **Owner:** the VP of System 3 Meta, once approved; the role can be held by a person or an agent.
- **First brief:** the kernel map, at most 600k tokens, checked by principal-engineer (company/sibling/system3-meta/2026-10-17-vp-design.md).
- **Next decision:** the founder approves D1-D8 and creates and names Meta's repository.
- **Not doing:** capacity taken from First Light. Until First Light ends, Meta gets 1 of 14 agent slots and no builders.

### 4. Hybrid company with humans
- **Goal:** a company where people and agents hold roles on the same terms (brief in, record out, checked by someone else).
- **Owner:** the Meta VP. **Depends on:** 3, and the human-holder rules in the VP design §1 (inbox, a 2-working-day acknowledgement, a delay note before any due date is missed).
- **Next decision:** after the kernel map, which use case and which people.

### 5. Three more companies
- **Goal:** show that the kernel works beyond lessons: product research, social media, and one to be chosen. The brief's test is a higher-risk company with real infrastructure and an external measure of success.
- **Owner:** the Meta VP. **Depends on:** 3, and 4's human-role mechanics.
- **Next decision:** the third use case; the order of the three.

### 6. 100k lessons, internationalized
- **Goal:** 100,000 lessons across languages and regions (localization-lead, company/international/).
- **Owner:** head-of-product, with localization-lead and principal-pm-verticals.
- **Depends on:** 2 (the platform has to hold it); 1 and EXP-002 (scale what is shown to teach); brief supply (F-41 found about 100 build-ready briefs against 9,000 needed for 10k).
- **Next decision:** after First Light, the founder sets the target ramp and the first locales.
- **Not doing:** scaling before learner evidence.

### 7. Move to an open-source agent harness
- **Goal:** run the company on an open-source agent harness (OpenCode or another), not only Claude Code, so that roles can bind to different models and providers, including independent checkers on a different model family, and the startup's customers are not tied to one vendor (Meta brief §2 item 3, "decouple from Claude").
- **Owner:** to be named (tools-lead with principal-engineer; the Meta VP for the kernel side).
- **Depends on:** the kernel map's "coupled to Claude Code / this host" class (hooks, `.claude/agents`, worktrees, permission modes, the Agent tool as dispatcher), and a model binding per role.
- **Next decision:** the founder starts it; then a spike that runs one role end to end (for example a fact-check) on the open-source harness against the same gates, and compares it.
- **Not doing:** dropping Claude Code before a second harness passes the same gates.

### 8. Token efficiency
- **Founder's ask (2026-10-19, conversation):** "one other thing is token efficiency we should have big project on that."
- **Goal:** more published, verified lessons (and more finished work of every kind) per token, without relaxing any gate. Every other project spends tokens, so this one raises the ceiling on all of them, and for Meta it is part of the product: a harness that makes checking cheap is easier to sell.
- **Why now (from the records, read 2026-10-19):** the ledger holds 113M measured subagent tokens (10-12 to 10-16) against 720 published lessons, about 157k per published lesson. Yield swung from 9.3 published per M tokens on 10-14 to 0.70 on 10-16, when manager rounds took 35% of spend and builds 8%, and about half of that day's verifications re-checked claims reset the same day (company/engineering/operations/2026-10-16-throughput-diagnosis.md). The model is unrecorded for 86% of spend, the coordinator's own spend is not measured at all, and the ledger stops at 10-16. At ~157k per lesson, project 6 would cost about 16B tokens.
- **Workstreams:**
  1. *Measure.* Ledger complete and current; coordinator spend measured; model recorded on every dispatch; the token unit confirmed and priced in money (O7 in company/decisions/2026-10-18-founder-category-scale-out-plan.md). A daily yield figure (published per M tokens) on the status page.
  2. *Stop paying twice.* Claims that do not reset on unrelated edits; brief-stage checks for "told, not shown" and answer leaks, which cause about half of revisions (O3); no build without a path to publish (O6).
  3. *Cheaper checking.* Claim scripts for computable claims (O1); a claim cap per content type (O2); lesson families, so one engine and one review cover many lessons.
  4. *Right model per role.* Model tiering: a cheaper model where an A/B shows no loss on the gates, the strongest model for learner walks and sensitive review (O4). This is also the first use of project 7's model binding per role.
  5. *Less coordination.* Event-driven rituals, one board writer, fewer and shorter manager rounds, and smaller briefs and context per role (O8; the roles keep/remove draft).
- **Return measure:** published lessons per M tokens, and tokens per verified claim, both measured weekly by analytics-steward from the ledger. Proposed target (founder to set): from ~157k to under 50k per published lesson by the end of Q1 2027, with gate results no worse (learner-review launch rate, fact-check dispute rate, QA pass rate).
- **Owner:** to be named. Proposed: principal-engineer-ops (already watches token burn rate), with portfolio-manager (ledger, money), analytics-steward (yield metric, model A/B) and tools-lead (instrumentation).
- **Next decision:** the founder starts it and names the owner; then a one-page proposal with a tranche-1 budget. Tranche 1 is measurement (workstream 1) plus the model-tiering A/B, because every later saving has to be shown against a baseline. O1, O3, O4 and O7 already have owners on the board; this project collects them rather than duplicating them.
- **Not doing:** savings that weaken an independent check, merge a builder with its checker, or skip a gate. Every change is compared on the same gates before it is adopted.
