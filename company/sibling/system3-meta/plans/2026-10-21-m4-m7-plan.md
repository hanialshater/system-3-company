The design follows Benchmark 5 (prototype/BENCH5.md). The vanilla agent cost $1.66 against the company's $14.15, and the company's defects sat at its seams. So:

- **One builder per lesson.** Split only for independence (fact-check, learner review), which the constitution requires.
- **Every gate is the company's own tool, wrapped by an adapter.** Nothing is re-implemented, except a 20-line claim floor that is not exported, and that has a parity test.
- **Every kernel feature below names the run step that fails without it.**

Hard constraints, enforced in code and not by prompt:

- never deploy;
- never edit `company/constitution/protected-paths.txt` paths (tools/company.mjs, tests/qa/**, src/kit/Lesson.tsx, ci.yml, company/reviews/README.md, the hook);
- a builder never verifies a claim;
- no new npm dependencies, because the adapters use only `node:` built-ins.

## 2. The lesson flow (`flow` in s3c-lessons.json)

| # | stage | signer | runs | pass rule / evidence |
|---|---|---|---|---|
| 1 | build | builder (demo-builder) | agent session in the order worktree | evidence: `src/demos/<d>/<slug>/`, `company/reviews/<slug>/design.md`, `build.md` |
| 2 | test1 | code | `adapters/s3c/gates.mjs <slug> --stage=build` | 0 check errors prefixed `src/demos/<d>/<slug>`; `build.md` has `## Pre-flight v<meta.version>`; design.md exists; status `review`; claims all `unverified` (builder never verified); copy-tells as advisory findings only |
| 3 | qa | code (async job) | `adapters/s3c/qa.mjs <slug>` | new `<date>-qa.md` reads `result: **pass**` and `lesson version: v<meta.version>`; reveal-fit exit 0 (exit 3 = "no evidence", stage errors, not revise); a11y `verdictAuto` passed as advisory findings |

| 6 | learner | role learner-evaluator, independent | agent session; pack = **only** `artifacts/walkthroughs/<slug>/` + `company/reviews/_template-learner-review.md` | post-check `learner-verdict.mjs`: launch + version === meta.version → pass; revise → build; fatal → park |

| 8 | gates | code | `gates.mjs <slug> --stage=ship` | claim floor + `readiness()` from tools/lib/readiness.mjs both empty |
| 9 | ship | release (release-manager identity; code executes) | `adapters/s3c/publish.mjs <slug>` | `node tools/company.mjs publish <slug>` exit 0 and meta.status `published` |

Why walk comes before check: the fact-checker role must read the transcript first.

How revise works:

- A revise from 5 to 8 goes to build with findings, as today. The builder fixes the text and bumps `version`. Stages 2 to 8 then re-run on the new version, which is exactly the company's current-version readiness rule.
- A ship failure is routed by reason (K11):

| `company publish` reason line | Routed to |
|---|---|
| `claims not verified` | check |
| `learner review` | learner |
| `QA:` | qa |
| `active publish hold` | park + ask to head-of-product |

`flowProblems` is satisfied: a `check` stage signed by neither builder nor orderer, and `ship` last. No `release` stage exists, so **deploy is not in the flow**.

## M5: governance in code

**Exit criterion:**

1. Kernel tests show each of these refused or escalated, with an event and an exit code:
   - an order whose *charged* spend exceeds its budget (planner refuses new sessions; ask `kind:budget` to the right decider);
   - a session over the per-lane cap;
   - a deploy, push or `[deploy]` attempt (guard event, session continues);
   - a protected-path write;
   - a builder signing any independent stage;
   - a fact-checker changing claim text (claims-guard refuse);
   - a revise loop over maxLoops (park + ask);
   - a publish hold (park + ask, no session spent).

### What "a full cycle of the operating loop" can honestly mean in a compressed run

The company's loop has three clocks.

| Clock | Rituals | What a compressed run can do |
|---|---|---|
| Event counters | retro / 5 merges, wbr / 10 merges, demo-crit / 4 reviews, launch-review / batch, design-review / 2 reviews | Fully real in a compressed run. Meta's work produces the events, and K21 exports them to the counters the company uses. |
| Short clocks | founder-digest 12 h, wbr 24 h fallback | Real only if the run actually spans 12 to 24 h of wall clock. They read git commit times (tools/lib/ritual-records.mjs), so they cannot be faked by advancing Meta's injectable clock without lying to the company's own tooling. |
| Long clocks | ops-review 168 h, demo-crit 7 d calendar, cycle-planning 14 d | Cannot be completed in a compressed run. They are covered only because they are overdue now: the cycle clears the backlog once. It does not show Meta holding them on cadence. |

So M7 claims **one event-driven cycle**: from clearing every overdue ritual, through one production loop that triggers retro, demo-crit and launch-review by its own events, to the next WBR, over at least 24 h of wall clock and with K22 restarts surviving. It does **not** claim a calendar week or a planning cycle. A real 7-day cadence run (weekly ops review, the second demo crit, cycle-planning at 14 d) is the follow-on, and it is the same run as M5's "founder runs a week from the queue alone". Both milestones' week clauses should be judged together, on one real week.
