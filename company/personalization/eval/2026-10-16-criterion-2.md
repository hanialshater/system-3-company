## §I. The review-timing candidate interface (for P1 and P2; read this section and nothing else of this file)

Published first, before the rest of criterion 2 exists, so the candidate is built blind to the judge (batch 3 V5). It says what a review-timing policy decides, what it costs, what it sees, the signature it exports and the baseline it is judged against. It says nothing about the simulated learner. If anything here is unclear, ask on W-1545 in writing; do not read the harness to find out.

### I.1 The decision

The world runs in sessions, one per simulated day, starting at the same clock time each day. At the start of every session, before any new card, the policy is asked once: **which completed lessons come back in this session, and in what order.** That is its only decision.

- A lesson is eligible if it is in `history` (completed at least once, before or during the episode). A lesson not returned is not revisited in this session; it can be returned in any later session. There is no "retire" decision: a lesson the policy never returns again is simply never asked again.
- New cards are not the policy's decision. In criterion 2 the new cards after the revisits are always chosen by `default-order` (batch 3 V1), the same for the candidate and the baseline.

### I.2 What a revisit is and what it costs

- A revisit is the product's revisit card: the learner is asked to recall before being shown (src/kit/progress.ts header). Its result `{ at, correct }` is appended to that lesson's `recalls` and is visible to the policy from the next session on.
- **Revisits come first** in the session, in the order returned (AMD-008 F2: due revisits before new lessons).
- **A revisit costs a feed slot.** A session has `slots` card positions. Each revisit takes one, so every revisit is one fewer position for a new card in that session. The session can end after any card, revisit or new, at the learner's choice; the policy is not told when or why, and cannot assume the learner reaches the new cards.
- The policy is never told how its revisits are scored. The judge reads recall from the learner at times fixed by the criterion and independent of any policy's schedule; reading does not change the learner and is not a revisit. Do not try to infer or target those times (V5).

### I.3 What the policy receives (permitted inputs only)

Exactly this object, built by the harness. Nothing else is available, and the policy must read nothing outside it (no clock, no environment, no files, no random numbers).

| Field | Content | Raw input and status (model.ts `INPUT_PRIVACY`) |
|---|---|---|
| `now` | Session start, ms since epoch. Use it only for per-lesson elapsed time (`now - completedAt`, `now - recalls[i].at`), as `revisitDue` in src/kit/progress.ts does. | clock of the session, not personal |
| `history` | `HistoryItem[]` as in model.ts: `{ slug, completedAt, predictedCorrectly?, recalls: { at, correct }[] }`, oldest first. `predictedCorrectly` `null` or absent means no prediction, never "wrong" (P2). `recalls` is cut to results with `at >= now - 30 days`. | completions (standing-conditions), recalls (standing-conditions; F1 30-day window), predictedCorrectly (conditions P1-P4) |
| `dims` | `Record<slug, LessonDims>` for every lesson in the catalog, the same objects the composer sees. | lessonDims, curriculumGraph (not-personal) |
| `slots` | Card positions in this session (an integer). | not personal |
| `fixedDue` | The slugs the baseline schedule (I.5) would bring back now, in its order. Given so the policy can say where it departs from it (V4); it may ignore it. | derived from completions and recalls only |

Not given, and must not be derived: anything in model.ts `FORBIDDEN_INPUTS` (session count, session length, dwell, device, persona label and the rest); learner-level days since last session (`gapDays`, refused, privacy ruling §2.5); any count or schedule of sessions; any hidden state of the learner. Per-lesson elapsed time from the timestamps above is what the product's own schedule already uses, and it is permitted here on that ground; if privacy-reviewer rules otherwise, the candidate is refused, not adapted.

### I.4 The signature

The candidate is one file under company/personalization/model/sim/ (P2), registered in `POLICIES`, exporting this constant. Copy the types verbatim; `HistoryItem` and `LessonDims` are model.ts's.

```ts
export type ReviewTimingInput = {
  now: number;
  history: HistoryItem[];
  dims: Record<string, LessonDims>;
  slots: number;
  fixedDue: string[];
};
export type ReviewTimingDecision = {
  /** Ordered: served first to last, before any new card. */
  revisits: { slug: string; reason: string }[];
};
export type ReviewTimingPolicy = {
  name: string;      // the POLICIES entry
  version: string;   // with a change line in company/decisions/2026-10-16-personalization-model-v0.md
  decide: (input: ReviewTimingInput) => ReviewTimingDecision;
};
export const REVIEW_TIMING_POLICY: ReviewTimingPolicy;
```

The harness enforces, before scoring, and marks the candidate **INVALID** for the whole run on any breach:
1. **Pure and deterministic.** The same input gives the same output, in any process (replay test). No `Math.random`, `Date`, `process`, I/O or module state carried between calls.
2. **Does not mutate** its input.
3. **Well formed.** Every `slug` is in `history`; no slug twice; `revisits.length <= slots`; every `reason` is a non-empty string a learner could read later (P2 item 4), naming an act ("you got this right 3 days ago"), never a trait or comparison (privacy P3).
4. **Reads only the fields above.** The harness adds forbidden fields (for example `sessionCount`) to the input and checks the output does not change.

### I.5 The baseline it is judged against

The product's fixed schedule (src/kit/progress.ts, `REVISIT_SCHEDULE_DAYS = [1, 3, 7, 21]`, `revisitDue`), applied to every lesson in `history` at each session start:
- `successes` = correct results in `recalls`; after 4 successes the lesson never comes back.
- `last` = the time of the latest result, or `completedAt` if none. The lesson is due when `now - last >= REVISIT_SCHEDULE_DAYS[successes]` days. A failed revisit leaves `successes` unchanged and restarts the wait from the failure.
- All due lessons come first (AMD-008 F2), oldest `last` first, ties by slug; if more are due than `slots`, the rest wait for the next session.
- New cards in `default-order`.

V4 (batch 3): if the candidate ever brings a lesson back later than this schedule would, any live use needs an AMD-008 F2 amendment first. The harness reports, per episode, how often the candidate's revisits were later than, the same as, or earlier than the baseline's for the same history; it is reported, not a pass input.

## 1. The world, the episode and the metric

### 1.1 The episode (harness/c2/world2.mjs `EPISODE2`)
- One simulated learner has one session a day at 09:00 UTC on days 0 to 13 and returns every day (as in phase A). The visible pre-history before day 0 is phase A's generator, unchanged (same history at a seed and persona).
- **A session has 12 card positions** (the feed's `MAX_REVISITS` is also 12). It starts with the review rule's revisits, in its order (AMD-008 F2). The order rule's new cards fill the remaining positions. The learner may stop after any card, revisit or new (§1.2 L5).
- **Arms.** An arm is an order rule plus a review rule. The **reference arm** is `default-order + fixed`, the product as specified: progress.ts schedule, due revisits first. Ordering arms vary the order rule and keep `fixed`. Review arms vary the review rule and keep `default-order` (V1).
- *Note, not a rule:* src/components/Feed.tsx today interleaves revisits (one per three new lessons) rather than putting them first. Criterion 2 follows AMD-008 F2, the governing rule for First Light, as the interface says (§I.2).

### 1.2 The learner (harness/c2/learner2.mjs; started as a copy of phase A's learner.mjs, which is not edited)

### 1.3 The metric: retained knowledge at a final test

**Primary: R₇ = K(T₇) / N_ref.**
- **K(T)** is the learner's expected knowledge at time T: the sum over all 250 in-pilot concepts of the share kept above the guess floor (0 if unknown). It is an expected value, read without changing the learner (T7d).
- **T_H** is H days after the start of the last session (day 13), with **no session in between**. Primary H = 7. H = 1 and H = 30 are reported.
- **N_ref** is the number of lessons the reference arm had completed by the end, pre-history included, at the same persona, seed and cell. It is the same number for every arm judged at that seed.
- Units: R₇ is "lessons' worth of knowledge kept a week after the last session, per lesson the product as shipped had completed". Δ between two arms is (K_a − K_b)/N_ref per seed.

**Why this form, and how it resists "revisit early" gaming** (the VP's requirement, batch 3 K1):
1. **One read time for every arm, not per-lesson probes.** I refuse the VP's example of probes at fixed delays after each lesson as the pass input. A review rule controls timing, so it can revisit a lesson just before its probe (for example at day 6 for a 7-day probe) and inflate the probe without durable learning. The final test is read at one time for all lessons and arms. That time is not in the review rule's input (T8). The interface says the rule is not told when recall is read (§I.2), and the episode length is not published to builders (§I.6). A rule that wants a fresh trace at the read has to keep traces fresh every day, and it pays for that in every session.
2. **Every revisit costs a feed position**, so it costs a new card or ends a session (L5). The primary sums over a **fixed set** (all in-pilot concepts) with a **fixed denominator** (N_ref, from the reference arm). There is no per-lesson average whose denominator a rule could shrink by teaching fewer lessons.
3. **Early revisits buy no durability** (L2). Only a revisit after some forgetting lowers the rate. A revisit just before the read raises K only through the clock reset, and only if the rule can time it, which point 1 prevents.
4. The H = 7 read sits 7 to 21 days after each episode lesson's completion. The read interval is not short enough to favour cramming (the lag effect: the best gap grows with the retention interval). It also does not lean on extrapolating the exponential form beyond the 1-to-7-day window the forgetting evidence covers (F7). H = 30 is reported and marked as extrapolated unless E1 sources the form that far. **Primary H = 7 is set now. E1 cannot change it.**
5. The gaming probe (§5 T10): a fixture that revisits every completed lesson every session loses on R₇ in every persona at base. Each loses 0.06 to 0.19 per lesson, and new lessons completed fall by 12 to 27.

**Reported, never a pass input:**
- R₁ and R₃₀;
- R1d, the phase A–style next-session recall of new lessons, labelled "gameable by timing";
- new lessons completed, revisits, revisit share, cards, reveal share, moved share;
- for review arms, the V4 counts: revisits earlier than, the same as, or later than the fixed schedule would serve for the same history (a "later" count above 0 means AMD-008 F2 needs an amendment before any live use; V4).

Engagement is never a pass input.

## 2. Arms, pairs and the rule

### 2.1 The rule (phase A's, unchanged)
In one cell, arm A **beats** arm B when all of these hold:
1. **Wins in at least 4 of 6 personas.** A win has the lower end of the 95% t interval of Δ_p above 0 **and** Δ_p ≥ δ_min = **0.01**.
2. **No persona is harmed.** A harm is Δ_p ≤ −δ_harm = **−0.01** with the upper end of the interval below 0.
3. Every guardrail of the pair's kind holds in every persona (§3).

Across the sweep, a pair has one of four outcomes:
- **PASS**: beats in the base cell and in every one-at-a-time cell (14).
- **FAIL-SENSITIVE**: beats in the base cell but not in some one-at-a-time cell; the readout names the cells.
- **FAIL**: does not beat in the base cell.
- **INVALID**: any §5 arm test fails.

Corners are reported only. δ_min stays 1 point, as in phase A, on R₇'s scale (above the guess floor, per completed lesson). One point of R₇ is about 1.25 points of plain recall, so the bar is a little looser on that scale than phase A's. I say so rather than rescale it after the fact.

### 2.3 Ordering headroom: `oracle-order` vs `default-order` (pre-commitment 3)
`oracle-order` reads the hidden state. At each pick it serves the eligible lesson with the largest expected rise in K(T₇) if studied now. For an unknown concept, that rise is P(encode | hidden prerequisites) × the share kept at T₇. For a known concept, it is the rise from refreshing its clock. Ties go to the default order. Review stays fixed.
- **Reading: HEADROOM if it wins (§2.1 item 1) in at least 4 of 6 personas in the base cell, else NO-HEADROOM.** Harms and guardrails are reported, not applied: the oracle is a reference, not a candidate. Every one-at-a-time cell is reported beside the base cell.
- **What it can and cannot show.** It is greedy (one step), so it is a **lower bound** on what any ordering could gain in this world. A wider oracle might find more. NO-HEADROOM means "the best rule I could write with full knowledge of the hidden state does not move R₇ by 1 point". It does not prove that no ordering can. I say so in the readout, and pre-commitment 3 reads the result as written.

### 2.4 Review headroom: `oracle-review` vs `fixed` (V2). I judge it sound and build it.
At each session, `oracle-review` brings back every completed lesson whose hidden recall probability is below θ, lowest first, up to the slots. θ is chosen per (persona, cell) from {0.3, 0.4, …, 0.9}. The choice maximises mean R₇ against the reference on **tuning seeds 5001–5100**, which are disjoint from the scored seeds; ties go to the lower θ. The choice is made in K2 inside the run, and the manifest records θ. It is a selection rule written now, not a value chosen by me.
- **Reading: HEADROOM / NO-HEADROOM as §2.3, base cell, 4 of 6.**
- Choosing θ on separate seeds avoids reporting the best of 7 variants on the very seeds that score it. It is still one family of schedulers (threshold rules), so it too is a lower bound on what any schedule could do.
