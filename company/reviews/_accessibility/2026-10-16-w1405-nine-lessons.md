## Findings common to the batch

- **Reduced motion: pass, all nine.** No lesson CSS declares an animation or transition. `globals.css` also has a global `prefers-reduced-motion: reduce` kill rule. Zero running animations in every run.
- **Keyboard path: pass, all nine.** Native `<button>` and `<input type=range>` throughout (kit `Control`, `Slider`), visible default focus ring, logical DOM order, predict -> lock -> explore -> reveal reachable without a pointer. Sliders respond to arrow keys.
- **Names: pass.** Every control has visible text or an `aria-label`; sliders carry `aria-label` and a live `<output>`. Every stage svg has `role="img"` and a label that describes the picture at some state (see per-lesson notes where it does not follow the state).
- **Dark theme contrast: pass, all nine** (no text under 4.5:1).
- **N1 (focus drops to `<body>` when a pressed control disables itself).** Verified on one-circle: focus "Meets 50%", press Enter, `document.activeElement` becomes `BODY` (the button turns `disabled` because it is now the selected value). A keyboard or switch user must re-Tab from the top of the page after every chip press. The same code pattern (`disabled={... || x === current}` or disabled once used) is in order-of-the-bad-year, tax-now-or-tax-later, one-circle, best-of-twenty (model-count chips), zebra tiles and "Sort by code", more-digits "Build" buttons, twenty-flips "Clear taps", two-cells "Next total"/"Reset"; I verified the drop on one lesson and infer it from the identical pattern on the rest. Not a lock-out (Tab continues), so non-blocking. The same reasoning is already ruled for the lifehacks engines: `company/reviews/_accessibility/2026-10-15-w1111-pressed-mode-aria.md` (selected state = `aria-pressed`, stays focusable, re-press is a no-op). Cleanest fix is one decision at the kit `Control` level, then lessons follow. Route: **platform-engineer** (kit decision), then **demo-builder** (lessons). Board item below.
- **N4 (state changes are not announced).** In one-circle, twenty-flips, more-detail and best-of-twenty the status line (`.msg`, readouts) has no `aria-live`; the `svg[role=img]` label changes but a changed label is not announced. Slider `<output>` is live, so slider users hear their own value but not the consequence (counts). order-of-the-bad-year, tax-now-or-tax-later, zebra and two-cells already use `aria-live="polite"` on their status paragraph; copy that. Non-blocking. Route: **demo-builder**.

## Per lesson

### order-of-the-bad-year: pass
- svg label: "Balance over two years" while locked, then "loss first: ends at $55k" / "gain first: ends at $64k", follows state. `<p aria-live=polite>` carries the comparison text (both orders and both results), so the figure's information reaches a screen reader without the picture.
- Ghost (other order) is dashed grey vs solid line; labels "loss first"/"gain first" on the lines; never colour alone. Contrast in both themes clean.
- Note: "Gain year first"/"Loss year first" and the flow slider are 35px and 28px high (below the 44px comfort size, above the WCAG 2.2 24px minimum). Kit-wide, not this lesson's doing. N1 applies.

### tax-now-or-tax-later: pass
- svg label follows state ("A ends at $30,000, B ends at $24,000"); `aria-live` line gives the case text. The tax slice of each bar is a dashed outlined block with a "-$16,000 tax" text label, not colour alone. Light and dark clean. Slider 28px high (kit). N1 applies.

### zebra-sorts-before-apple: pass
- No svg; the stage is real text in buttons, so a screen reader reads it all. Tiles have explicit names ("Show the code of Z in Zebra", then "Zebra: Z is 90"). Order of the sorted words is the DOM order, with "first"/"last" text. `aria-live` status line announces each step. `Ignore case` carries `aria-pressed` and the on/off wording in its text.
- N3 (trivial): `<p aria-label=...>` on the "By code: ..." line; `aria-label` is not valid on a paragraph and is ignored, but the visible text is read anyway, so no loss. Delete the attribute when next in the file.
- N1 applies (tiles disable once read).

### more-digits-not-bigger: issues
- **A1. Light-theme contrast and colour-only state on the number labels.** The built digits of "0.3 / 0.25 / 0.125" use `fill: var(--domain)`; in light theme that is rgb(124,156,255) on rgb(236,239,246) = **2.26:1** at 15px bold (needs 4.5:1). Built vs not-built digit is shown only by that fill versus `--muted`, so the colour is also the only cue for "which digits are built" (the bar's growth and the "so far" number are second cues, so this is not a lock-out). Dark theme is 5.95:1, fine. Fix: use ink (`var(--fg)`, with a bold or underline for built digits) or the darkened-domain mix the economics lessons use. Owner: **demo-builder**.
- **A2. The explore state is unreachable to a screen reader.** The svg label and the live caption are fixed text ("Block = 0.1 · sliver = 0.01 · hairline = 0.001") after the prediction, whatever is built. The "so far" values (0.3, 0.25, 0.125) exist only as svg text inside a `role=img`, so a learner who builds digits hears nothing change and never gets the numbers being compared until the reveal. Fix: put the built values in the label and in the `aria-live` caption, for example "0.3 built: 0.3; 0.25: 0.2 so far; 0.125: not started". Owner: **demo-builder**.
- Colour-blind: the three piece types differ in width as well as colour (block / sliver / hairline) and the caption names them; ok.

### more-detail-less-likely: pass
- Two sliders with names and live values; svg label gives the counts ("100 librarians, 90 of them run a book club, of 1000 people") and follows both sliders. Nested rings are told apart by fill and by outline weight plus the counts in the readouts; no colour-only meaning. Light and dark clean.
- N4: status line and readouts are not live (slider values are).

### one-circle-fewer-introductions: pass
- svg label follows state ("circle meets in 50% of weeks; chance you meet 34%"); the chips are real toggles with `aria-pressed`. Every mark on the bar carries a percentage text. Light and dark clean (the only low reading was the selected-and-disabled "Meets 100%" chip, exempt).
- N1 verified here (focus to body after a chip press). N4 applies. Chip height 35px (kit).

### twenty-flips-run-of-five: pass
- H and T cells carry the letters, so a heads/tails sequence is never colour alone. The histogram bars "5 or more" are yellow and the rest grey, and the x-axis labels (3, 4, 5, 6, 7, 8+) carry the same information in text. svg label gives only the tallies ("1000 real sequences; 475 with a run of 5 or more"); the bin counts are not in text anywhere outside the picture. Acceptable because the key number is, and the reveal restates it.
- N4: tallies and the readout are not announced after "Run 1,000 real". N1 applies ("Clear taps"). Light and dark clean (dark `H` on yellow is 10+:1; the scanner's 1.24 was a false reading).

### best-of-twenty-on-one-test: issues
- **B1. Light-theme contrast of the winner label.** "winner 59" (and the fresh-test score) are svg text in `var(--domain)`: rgb(199,146,234) on rgb(236,239,246) = **2.09:1** at 11px bold. That label is the lesson's key number, but the same number appears in the "Winner, shared test: 59 of 100" readout in ink, so no information is lost; this is a legibility failure for low-vision learners. Fix: ink fill with the ring for emphasis, or a darkened domain mix. Dark theme clean. Owner: **demo-builder**.
- **B2. Results are not announced and the svg label is thin.** The "Seen: seed 1, 20 models: winner 56, fresh 49.7%." line is not `aria-live`; the svg label is only "20 models, winner 56" with no spread of the other models. Also `aria-label` says "1 models" (no singular; visible label code handles `m > 1`, the svg label does not). Owner: **demo-builder** (live region; fix grammar; consider "winner 56 of 100, others 44 to 54").
- Winner dot is ringed and labelled as well as coloured; other dots are grey. No colour-only meaning. N1 applies (model-count chips).

### two-cells-sum-any-range: issues
- **C1. Colour-only states, including a red/green pair.** Which running totals are stale after "Day 3 + 1" is shown only by a red tint (`--bad` 30%) on cells whose normal tint is the domain green (12%); the message says "(red)". Red against green is the pair most colour-blind learners confuse. The count ("6 of 8 stale") is in text, but which cells is not. Likewise the "in range" cells (domain border) and "ring" cells (foreground border plus domain shadow) are colour or border colour only. The ghost cells are dashed (shape, fine). Fix: add a text or shape cue to stale cells (a "stale" word or strike, "!" mark), and to in-range cells (underline or heavier border). Owner: **demo-builder**.
- **C2. Small label contrast.** The "to N" and "day N" labels on the cells are 10px at `--muted`: "to N" measured 3.58:1 in light (below 4.5:1 at this size). The numbers inside the cells are 15px bold and fine. Dark theme clean. Fix: raise to `--fg` or increase size. Owner: **demo-builder**.
- No svg here; the cells are real text and the live status line plus readout carry the sums ("Days 3–7: 24 − 5 = 19"), so a screen reader gets the answer. The two 8-cell rows are plain spans with no grouping or table semantics (read linearly as "day 1 3 day 2 1 ..."): fine, noted only.
- Sliders "from day"/"to day" are named, arrow-key operable and disabled until the totals are built (the live text says so).

## What I believe, and how sure

- No launch block: sure (keyboard path run end to end on all nine, both themes).
- The two contrast figures (2.26:1 digits, 2.09:1 winner label) and the 3.58:1 day labels: sure, computed from rendered colours on the server's build; `--domain` has no light-theme darkening for svg fills (`globals.css` darkens only `.tag.domain`).
- N1 focus drop: sure on one-circle; likely (same code pattern, not each run) on the rest.
- Colour-blind verdicts: moderately sure (markup read, no filter run). Screen-reader verdicts rest on names, roles and live regions in the DOM, not a listening test.
