See S3 |

Conditions (all are ways the build could make §5 false; none is a change to the design):

- **S1 (learner-model-engineer, in the build).** The state, the flags and the evidence object are never written: not to localStorage, not to the beacon, not to `exp`, not to the account merge or the export, not to a log. A test: run the function with the network and storage stubbed and assert zero writes and zero fetches. This makes "computed in the browser" checkable.
- **S2 (growth-designer, PRD-004 line 39, and platform-engineer when built).** PRD-004 says a signed-in learner's challenge state "is derived from server-side progress". EDD-009 §5 holds only if that means: the merge response writes D12/D13 rows into D1 in the browser and the **browser** then computes the state. A server-rendered challenge page that computes or embeds the state would be a server-side read of D12.3 / D13.3 / D13.4 that §5 says does not exist. Please reword the PRD line, or tell me if a server render is intended and I read it as new.
- **S3 (learner-model-engineer).** The §8 offline check on real account data needs its own privacy read before it runs, with a stated purpose, the rows, who sees them, and retention. A §5 pass is not that read. Until then the only evidence for `held` is the fixtures. I would pass an aggregate-only design (counts of recalled and held at next revisit, cells under 20 not reported) without a long review.

Evidence limit: I read the EDD and the progress code. Nothing is built, so S1 and S2 are conditions on a build I have not seen. Confidence in "§5 holds as designed": high, about 90%. I would say 75% that the first build meets S1 to S3 without a finding.

## `spacedDays` stays inside C2's allowed values: yes

Question: does the growth designer's definition in PRD-003 R12 and PRD-004 (commit 1c2f243) stay inside what C2 allows (`spacedDays` one of the schedule values 1, 3, 7, 21)?

- Definition: `REVISIT_SCHEDULE_DAYS[successes before this recall]`, successes = the lesson's `recalls` with `correct: true`, counted before this answer is appended.
- `src/kit/progress.ts` line 48: `REVISIT_SCHEDULE_DAYS = [1, 3, 7, 21]`. `revisitDue` returns false when `successes >= 4` (line 53), so a revisit card, and so an `exp` sender, can only run with successes 0 to 3, indices 0 to 3, values 1, 3, 7, 21. **Every output is inside C2's set**, and no output depends on elapsed time or on `?revisitMinutes` (the PRDs' day-5 and QA statements follow from that).
- It adds no field and no new information: the value is a function of the count of right answers on that lesson, which `recall` already implies. It is a strict narrowing of the elapsed-days value the existing recall event sends, which is why C2 would drop that one. My `exp` ruling is unchanged by it.
- One remark, not a condition: because `exp` is sent only on a lesson's first revisit, the value is always 1. That is constant and carries nothing. Dropping the field is allowed under C3 (strict subset, no re-review) and would be the smaller event. The analytics steward decides; I would not object either way.
- The existing `recall` event still sends elapsed days as `spacedDays` (rounded). That is the open item of my C1/C2 ruling (the route has no allow-list), not new here.

**spacedDays within C2: yes.**

## C8 early stop: my half

`C8 early stop:` **My half: yes, a founder-approved deploy may count as the early stop for a harm-condition stop of an experiment, on four conditions. Not for a privacy defect. This is my half only. backend-engineer is the co-decider, and this line has no force until she answers.**

Reasoning, from the purpose of C8, not its wording. C8 said an experiment "can be stopped without a rebuild" because both PRDs name a harm condition (-3 points). The harm there is to learning, over days, and the data at stake is one enum event with no identifier. A stop that takes the time to get a founder's approval for a one-line change to the server's registered-experiment list (C2's constant, which already carries an end date) does not leave learners exposed to a privacy harm in the meantime. The server drops an unregistered type with a 204, so a deploy stops collection even while old browsers keep sending. A deploy cannot be what I avoid: the principal engineer's review says, and I cannot check from this host, that any run-time switch on Vercel also needs a redeploy or a new dependency, and the company's rules would send both through the founder anyway. A condition I could not meet without a new dependency is not a condition I should keep.

Conditions on my yes:

- **E1 (analytics-steward, with backend-engineer).** The registered-experiment list is one constant in one file, so a stop is a one-line change with no other code in the diff, and the end date stays as the backstop (C2, C7). The registration for each experiment names its harm threshold, who reads it and how often. A stop-by-deploy that waits on a reading nobody takes is not a stop.
- **E2 (chief of staff, founder).** The stop-deploy is a recorded request type: the founder is asked for that deploy specifically, the request says what is being stopped and why, and the answer is on disk. "Every deploy needs the founder's approval" stands; this only makes this one's approval cheap to give. A target time for answering is the founder's to set (I suggest one working day). **Whether the founder wants a standing instruction is the founder's call; I flag it and do not decide it.**
- **E3 (backend-engineer).** Nothing about the stop depends on the client. In particular the sender must not need a rebuild of the **client** to stop sending (a flag read from a server response is a new request and a new read from me; do not add one without it). Browsers that keep sending are harmless once the server drops the type.
- **E4 (me, narrow).** This does **not** cover a privacy defect found in the event (an identifier, a free-text field, a token reaching it). For that the stop must be faster than a deploy request would normally be, or the field must not be accepted in the first place, which is C1 and C2 and why they come first. If one is found, the event type is removed from the server's accepted list in the same founder-approved deploy and I record it as an incident in the same file.

What this does **not** change. C8 has a second half, that the `exp` event sends nothing when the browser sends Global Privacy Control or Do Not Track. That is a client-side check in `track()` (the principal engineer found there is none, for any event), it needs no deploy to be effective once built, and it remains a go-live condition (P6.4). Nothing I say here defers it.

I wrote C8, so relaxing it is my own change of a condition I set. I do not take that as settled by me alone: it takes effect when backend-engineer answers (agrees, or names the reason a deploy is not enough), and the principal engineer records it in the C8 owner's task. If she disagrees, the options on the table are a per-request environment read (needs her read of Vercel's behaviour) or an edge-config store (a new dependency, so a decision record first); I would then re-read whichever she proposes for the data it holds.
