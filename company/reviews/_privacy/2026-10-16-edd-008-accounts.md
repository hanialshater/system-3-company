Where a claim below rests only on the spike's report, I say so.

## Verdict

**Conditional pass for the data model.** The schema holds nothing the gate forbids, and every column is enforced by the database or a hook with a test. The accounts code may merge to main **with `ACCOUNTS_ENABLED` off** and may run on the `first-light` test database with staff addresses and fake data once conditions M1–M6 hold. It may **not** take a real learner's email until the go-live conditions G1–G6 hold. Gate P1.7 fails today (DPA status "unknown"), and that blocks the surface, not the merge.

The data model is smaller than the gate's minimum set in one respect (no `settings` yet) and larger in the ways Q2 lists; each is ruled below.

## Answers to the backend engineer

### Q2: library-required columns and tables beyond gate 2.2. **Pass, with M1, M3 and the inventory.**
| Item | Ruling |
|---|---|
| `email_verified`, `updated_at` | Pass. No personal content; the library needs them. Put them in the inventory |
| `name` (`CHECK = ''`), `image` (`CHECK IS NULL`) | Pass. Always empty, database-enforced. The EDD sentence "Not stored anywhere: name" is true of `auth_user` only, and must say so until M1 closes the 300 s window |
| `auth_session` | Pass. Credentials plus times. The token is stored in plain form (the EDD says so); database access equals session access, so that is the principal engineer's and Neon access control's problem, not a gate row. 30 days, then purged |
| `auth_account` | Pass **as an empty table**: 0 rows from a magic link (test 17), credential columns forced NULL. `db-deletion-check --all-counts` must keep showing 0 at readiness and go-live. If a future library version writes a row, that is a stop, not a warning |
| `auth_verification` | Pass with conditions. It holds an email address for people who have not (and may never) created an account. Held until the **next** sign-in request purges it, not "300 s" (M3). Name guard M1 |
| `signup_intent` | Pass. Band, policy version and a hash of the link token; no email, no id; ≤10 min by `CHECK`. It cannot be tied to a person |
| `deleted_account` | Pass. Random id and time, 35 days; holds no learner data (P1.6). The purge that ends it must run at least as often as the shortest restore window needs; it is request-driven (M3) so it can only live **longer**, which is safe |
| `schema_migrations` | Pass. Created by `tools/db-migrate.mjs`, no learner data |
| Extra indexes in 001 | Pass. No new data |

I do not ask for any cut. The one cut I would take for free is `auth_account` if the library's schema check passes without it; the spike did not test that, and an empty table is harmless.

### Q3: inactivity notice versus P1.8. **Allowed in principle; not buildable or needed before 2028; two conditions.**
- No account can be idle 24 months before about December 2028 (accounts do not exist yet). So release 1 ships with the idle purge **off** (as the spike left it) and the retention sentence in the policy. Nothing is blocked now.
- The gate says email is for "sign-in and account recovery only" and "a new use needs its own review". This is that review: **one** account-status notice, sent to the sign-in address about 30 days before an idle deletion, is acceptable. It is a warning about the learner's own data, not a reminder or marketing. Conditions: plain text, no tracking, no progress or lesson content, no call to action but "sign in before DATE to keep your account", and it is sent at most once per account.
- I cannot put it into effect. It amends P1.8 in a gate that is still **proposed**, and I may not approve my own proposal. The founder takes it at the 10-23 review with the gate. Whether a notice is legally required, or the 24 months is right, is for counsel and the founder (F-25), not me.
- Building it needs a way to send once, which means a new column (for example `idle_notice_sent_at`), and a scheduled job. That is a new schema diff and its own review. Until then `IDLE_PURGE_SQL` must stay unreachable from any route (M2).
- If the founder says no notice: delete without one, and the policy and the sign-in email footer must say so. That is a worse outcome for the learner, not a privacy failure.

### Q6: "turning 16". **Conditional: self-service and one-way is acceptable; do not build it now.**
- In release 1 a 13-15 learner and a 16+ learner see **no difference**, because everything teen mode removes is absent for everyone. So the self-service move has no function yet, and a control that edits a protected attribute needs a reason. Build it when a feature differs by band, and not before the counsel answer on GDPR Art. 8 (gate 3.2, wanted by 11-09). If counsel says 13-15 need parental authorisation in 16-countries, release 1 goes to 16+ accounts only and this question disappears.
- When it is built: it is a new write route and a new schema diff for my review. It accepts only `13-15` → `16+` (enforced in SQL with `WHERE age_band = '13-15'`, so the server cannot move a band down); the year stays in the browser and the server receives only the band, with the same self-declared trust as at sign-up; the account view never prompts or nags about it (a prompt teaches the answer); no email "you may be turning 16", which would be a new email use and is impossible anyway without a birth year; `updated_at` moves, nothing else is logged.
- The band must never move down automatically. The route for a learner or parent who says "I am under 13" is deletion. Counsel should say what duty follows if we learn actual age (COPPA "actual knowledge"); flagged, not decided. The EDD names no contact route for a parent; the policy needs one.

## Findings the backend engineer asked me to rule on

1. **Better Auth stores IP and user agent by default; blanked by a hook plus a DB CHECK. Pass.** Two independent layers: `session.create.before` and `session.update.before` write `""`, and `CHECK (coalesce(x,'') = '')` rejects anything else (test 7: a value insert fails; stored rows are empty). Remaining use of the IP is the in-memory limiter only, which is processing and not storage; the policy says so. Condition M5: the hook test is part of the regression suite on **every** Better Auth bump (patch included), as the principal engineer proposed.
2. **`name` could sit in `auth_verification` for up to 300 s if code calls the library directly. Conditional; fix before merge (M1).** Today the only door is `start`, which refuses any key but three (test 3), and `signInMagicLink` has one caller. That is a code convention, not an enforcement, and the EDD's own goal is "enforced by the database where possible". Ask: either a `verification.create.before` hook that strips `name` from `value`, or a `CHECK` that `(value::jsonb ->> 'name')` is null or empty (the table is written only by this plugin, so the cast is safe; the spike picks the safer of the two), plus a test that calls the library directly with a name. Until M1 closes, the EDD wording "name: not stored anywhere" must be qualified. Related, accepted: a missing-band call writes an orphan `auth_verification` row with an email for up to 300 s before `sendMagicLink` refuses (test 10); unreachable through `start`.
3. **The cookie is scoped to `/api/account`. Pass for P6.2, conditional for P1.2 (M4).** The real-browser run (0 of 5 beacon requests carried it, `/api/account/me` did) is the evidence the gate asked for. Path scope keeps the cookie off the beacon and pages; it is not a security boundary against other same-origin code, which is why `HttpOnly` matters and is set. It is a first-party session cookie set only after sign-in and needed for it, so no consent banner follows from it (P5.7); counsel confirms. Lifetime is 30 days (Q8).
4. **Processors, P1.7: fail today, with specific asks.**
   - **Vercel:** listed correctly (IP, user agent, path including the link token, cookie on `/api/account/*`). Two corrections: (a) §10 says functions are in Frankfurt, but SPIKE-002 R1 found `preferredRegion` does not place a Node function, so until deploy config sets `fra1` and `x-vercel-id` shows it, account requests, emails and progress maps may be processed in the US. The row must read "intended, not yet in place" (G3). (b) The link token sits in the logged URL; it is hashed at rest, single-use and dead in 300 s, so I rate it low, but log retention is unverified (E13).
   - **Neon, EU:** the test database `first-light` (Development and Preview) may hold only fake data and staff addresses; Production is a **separate project at go-live**, created in Frankfurt, not a branch of `first-light` and never the reverse (principal C8). P1.7 for Neon cannot pass until the Production project exists, its region is read from the dashboard, and the DPA path (billing and contract run through Vercel) is settled by counsel. I will accept a screenshot or API read of the project region as evidence.
   - **Resend:** "tracking off" is a **sending-domain setting**, not something our code can enforce per email, so it is a claim until shown (G2): the founder reads the domain's open and click tracking as off, and a delivered test mail shows the link in the raw message is our URL, not a Resend redirect. Region, log retention, whether a logged email can be deleted, and the DPA are unknown (counsel, F-25). Resend keeps the learner's address and a dead sign-in link in its own log, and our deletion cannot reach that; the policy must say it. Until F-23, Resend's shared sender reaches only the account owner, which is enough for staff testing.
   - **Better Auth** is not a processor. True only while telemetry stays off: `telemetry.enabled:false` is not enough because `BETTER_AUTH_TELEMETRY=1` in the environment turns it on (spike Q6). G4 puts that in the readiness checks.

## Other findings

- **F-a: the idle clock is wrong for active learners (M2).** Retention keys on `last_sign_in_at`, which changes only when a session is created. Sessions last 30 days and slide forward on use (`updateAge` one day), so a learner who stays signed in for two years never creates a session and looks idle. When the idle purge is switched on it would delete the account of an active learner. Use the latest of `last_sign_in_at` and the newest `auth_session.updated_at` (no new column), and test it.
- **F-b: the retention claim "300 s" is not true as built (M3).** Expired `auth_verification`, `signup_intent`, `auth_session` and old tombstones go in `purgeExpired`, which runs only inside `start`. In a quiet period a pending email can sit past its expiry for as long as nobody starts a sign-in. Either state it honestly ("removed at the next sign-in request, normally within hours") with a readiness query for the oldest expired row, or ask the release manager for a daily cron (deploy config, founder approval). Both are acceptable to me; the false sentence is not.
- **F-c: the rate limiter keeps raw IPs and emails in memory, contradicting its own comment (M6).** `http.ts` says "Keys are hashed so the map never holds an address", but `start` passes `ip:<ip>` and `email:<email>` as keys unhashed, and entries are only evicted above 10,000. In memory only, per instance, never logged, so this is low severity; the comment is a false statement about privacy, and hashing the key is two lines. The library's own limiter also holds IPs in memory.
- **F-d: `policyVersion` is client-supplied and only format-checked (M6).** `policy_version` is "proof of what was agreed", but the server accepts any string matching `[A-Za-z0-9._-]{1,32}`. Check it against the list of published versions.
- **F-e: a sign-in link can be sent to an address the sender does not own.** Same answer whether or not an account exists (good, no enumeration), 5 per minute per IP and per email. Accepted; the email says "if you did not ask for it, ignore this". The token is not an account until clicked, and an account is created only on the click.
- **F-f: the limiter on `/magic-link/verify` (5 per minute per IP) may lock out a shared school address.** Not a privacy issue; noted for the principal engineer.
- **F-g: audit is clean for what the spike adds** (0 in the runtime tree); pre-existing `vercel` CLI advisories are platform-engineer's.
