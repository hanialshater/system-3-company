## Verdict

**Design: pass with conditions (E1 to E14 below).** The EDD adds no field, no write, no fetch and no stored derived value, and reads only the learner's own device record (D1) through the Feed's existing call. That is inside my N1 to N3.

**Merge with the flag off: no privacy objection**, provided T1 and T10 hold (nothing a learner sees changes and no candidate code ships in the built output), and E12 below.

**Release to learners (flag on): NOT cleared by me, and three things I cannot clear stand in the way:** (1) counsel on W-1766 (13 to 15 year olds, no way to turn it off); (2) the W-1764 amendment, ratified by the founder, because AMD-008 P4 as drafted still requires an off switch and my own earlier conditions (D2, G3, T3) rest on it; (3) the conditions below met **in code**, which I verify when the code exists. Confidence that the first build meets E1 to E14 without a finding: about 65% (same figure and reason as my T2 ruling: a serving layer adds surfaces I have not seen).

## What I can rule on myself, and what is for counsel (plain statement)

I can rule on: whether the design leaks data, stores derived values, reads forbidden inputs, or shows facts about a learner it should not (Q-P1 to Q-P7), and whether the flag and withdrawal path are adequate **as a company control**. I have done that below.

Counsel (W-1766; the founder routes it; I decide none of it):
1. **13 to 15 year olds, personalised with no off switch and no objection right.** Whether UK AADC (profiling "off by default" for children unless there is a compelling reason), GDPR Art. 21/22 and recital 71, or comparable law requires a learner control or an objection right for this kind of automated ordering. My earlier D4 (minors in a personalised default arm) was about an experiment arm; this is the same question made permanent and universal, so it is **harder** than D4, not the same. The age band is not an input (T1) and must stay out of the code: if counsel says "minors need a control", the answer comes from a control or from a population rule at the account level, never from branching the model on age. Note that anonymous learners may be under 13 and cannot be identified as such (T5), so any answer that treats under-13 differently cannot be implemented by the website part at all.
2. **Whether on-device-only ordering is "processing" by us at all** when nothing leaves the device (it may narrow the legal question; it does not change my engineering conditions).
3. **ePrivacy storage rule (new, raised by this EDD).** D1 (`s3c:progress:v1`) is recorded in the inventory as storage "strictly needed for the feature the learner uses" (spaced revisits the learner asked for). Reading it to reorder every learner's feed is a **new purpose for existing stored data**, and with no switch it is arguably not a feature the learner asked for. Whether the strictly-necessary exemption still holds is counsel's. Until counsel answers, D1's purpose cell is stale (E13).
4. The standing items carried from earlier rulings: lawful basis cells "unknown (counsel, F-25)"; "less of this" as special-category by implication (not used by this EDD).

A "company flag, off by default" is a good control for the company. It is **not** a substitute for a learner's control as far as counsel's question goes, and I will not describe it as one.

They stay in force for the settings API if it is ever built-on.
- **T3 of the model-inputs ruling** ("the off switch is as reachable for a teen as for anyone"): **lapses for the website ordering, by the founder's decision**, but only once W-1764 is ratified. Before then my earlier text stands as drafted (the stricter text wins until amended, as I said in section 7 of that ruling). I do not waive a founder-ratified requirement myself, and a proposed amendment is not a ratified one.
- **Unchanged and now carrying more weight:** N1 (computed, not stored), N2, N3, section 4 (stored fingerprints refused), T1/T2/T4/T5/T6, P3 (no traits, no comparison, no pressure), M3 (estimate never shown as a number or trait). With no escape hatch, these are the whole protection.
- **No false comfort in copy:** nothing a learner reads may say or imply they can switch the order off, set it, or that it reflects their choices (SS3: stated means stated). The EDD adds none; E10 keeps it that way.

## Answers to Q-P1 to Q-P7

### Q-P1. Is display order and reason state held in React memory "stored" under D20/N1? **No, with four conditions.**
Reasoning from purpose: D20/N1 exist so that nothing derived outlives the moment of use or reaches a place a person or a process can later read it. State that lives in the page and dies on reload is the same as the `ComposeInput` objects N1 already allows in memory. A page-life value is not a field with a deletion path to worry about.
- **E1.** The order, pins (`h`), reason codes and `R` are held only in component state/refs or a module variable. Never in `localStorage`, `sessionStorage`, cookies, IndexedDB, Cache API, `history.state`, the URL (query or hash), `window.name`, a service worker, or any global an extension convention reads. A module-level cache that survives client-side navigation is allowed (it still dies on reload); one that is written to storage is a stored derived value (refused, section 4 of the model-inputs ruling). Test: T3's stubs plus a post-run diff of every storage area and `history.state` showing zero change attributable to the ordering path.
- **E2.** The values are not put in the DOM beyond what the learner sees: no `data-*` attributes, hidden inputs or `aria` strings carrying a reason code, rank, run position or pin (an extension or a screenshot tool reads the DOM). Test: render with a seeded history, assert no attribute value matches a reason code name or `R` index. (Visible reason copy is the one allowed output.)
- **E3.** No error path emits the order. T13 covers console and network; add error boundaries, `window.onerror`/`unhandledrejection` handlers and any Next error reporting: none may include the order, a history item or a stack that names them. (The EDD's no-logging rule already says this; this makes the error-handler surface explicit.)
- Note: bfcache may keep the page's memory for a back/forward navigation. That is the same lifetime class; I accept it.

### Q-P2. Slug-bearing requests (lesson chunk loads, `/api/meta/<slug>`, `predict`/`reveal`/`complete` and `view` beacons) now follow the personalised order. **Ruling: accepted, with conditions E4 to E6. No batching and no beacon change.**

What I checked rather than took on trust:
- `track()` sends `{type, slug, ...}` by `sendBeacon` to `/api/events`; `events-intake.ts` logs an explicit pick of fields, adds `at` itself, and "no identifier is read or added: no cookie, no IP, no user agent, no session id". Beacons from one device cannot be joined to each other by us. D6 has "no identifier, so a single learner's events cannot be found or deleted".
- The beacon **already carries what the order is computed from**: `predict` has `correct`, `complete` is the completion, `recall` has `correct` and `spacedDays`. So for events sent from this site, the order the server could infer is a function of data it could already see, and the lesson-view stream already says what a learner is doing right now. The new thing is the order as an *output*, and it is derived from inputs that went out as events (when events are on and the history was made on this site). The marginal disclosure is only about history the beacon never carried: progress made with `NEXT_PUBLIC_EVENTS=off`, or history merged from an account on another device (EDD-008). That is small and needs a device-level join that the design does not give anyone.
- The only link between requests is the host's own request log (IP, user agent, time: D7), which is Vercel's, not ours, and exists today for the default order too.
- No derived value, reason code, rank or "moved" marker is sent. Nothing is added to any request.
- The signed-in session cookie is scoped to `Path=/api/account` per ADR-008 (cited in `src/lib/server/personalization/settings-wiring.ts`; I did not read the cookie code, the accounts branch is not here). Lesson chunks, `/api/meta/<slug>` and `/api/events` are outside that path, so **a slug-bearing request does not carry the session**. This is what keeps "the sequence of lessons a signed-in teen opens" from being tied to an account by our code.

Why not batching or hiding the sequence: a batched beacon puts a whole ordered list of slugs into one payload (strictly more than one slug per event), and "no slug in the beacon" would remove the product analytics that D6 exists for. Both make the privacy picture worse or break a lawful purpose to fix a smaller exposure. Refused as remedies.

Conditions:
- **E4. Request shapes frozen.** With the flag on, the set of requests and each request's fields equal the flag-off set (EDD T11 already counts chunks; extend it to the beacon fields and `/api/meta`). No ordering-dependent prefetch, no prefetch of a lesson that a learner has not been shown or neighbours (`active ± 1`, as today). Test (verify): record requests for a scripted session with the flag on and off; the multiset of (method, path-without-slug, body keys) is identical.
- **E5. No server-side sequence reconstruction.** The W-706 persisted-events design must not add a session id, device id, IP, cookie or any key that lets events be ordered per device (gate P6.2 stands), `at` stays server-set, and nobody joins the host's request logs (D7) to event rows. This is a standing condition on W-706 and on analytics-steward's queries; if either wants a per-device sequence it is a new read. Test: the intake allow-list test (`events-intake`) still fails on any added identifier key.
- **E6. Session cookie scope.** The session cookie keeps `Path=/api/account` (or narrower). If it widens (for example to `/`), this ruling lapses for signed-in learners, because every lesson-chunk and beacon request would then carry the session. Test (backend-engineer, accounts branch): assert the `Set-Cookie` path, and assert that a request to `/api/events` and to a lesson chunk in the test client sends no session cookie. Unverified until then.
- The residual (a party who sees the host's logs could infer part of the order from one device's request sequence) is accepted as **low and already present in kind**; I state it in the release note for the founder (E14), not hide it.

### Q-P3. May option E's single static chunk count as no fetch "beyond today's"? **Yes, with two conditions.**
A static asset with the same URL and bytes for every learner discloses nothing about a learner. The word in N1/N2 is about learner-derived requests. Conditions:
- **E7a.** The chunk is requested **unconditionally** on feed mount when the flag is on (same for a new device and for a device with 500 completions). A load conditional on history, on `progress` being non-empty, or on any learner state would tell the CDN something about the learner's device, and is refused.
- **E7b.** EDD T11's "same number of chunks" assertion is amended to say what is true (one extra, fixed chunk, same for all learners), so the test cannot be satisfied by accident. Option A (bundled) remains my preference: no request at all.

### Q-P4. Is the company build flag plus the withdrawal path the replacement for the D2/G3 off-switch conditions? **Yes as the *company's* control; no, it is not the learner's, and counsel has not said it is enough. Pin it (Q-O1): yes, required.**
- **E8. The flag is build-time only and cannot be turned on unseen.** Read once at build; no run-time fetch of a flag, no remote config, no cookie, query-string or localStorage override (so no way to opt a device in or out, which would be a hidden learner control and a second code path). The deploy script pins `NEXT_PUBLIC_NEW_LESSON_ORDER` from the approved release, as `SHOW_REVIEW` is pinned (Q-O1; release-manager, platform-engineer). Until it lands, the release record carries the build log line `new-lesson-order: on|off`. Test: an environment with the variable set to a non-`reachable-v2` value builds "off"; a dashboard-set value that differs from the release record fails the release check.
- **E9. What turning it on needs, as a written release record, before the founder is asked:** W-1764 ratified, W-1766 answered (G9), the privacy conditions here met in code (my sign-off on the diff), RC's copy approved (W-1758), F6 reported, K6/G GO. Turning the flag on without any one of them is the withdrawal trigger in G10.
- **Time to withdraw.** The EDD says up to a remote build plus ten minutes, and every withdrawal is a deploy needing the founder. For a **privacy** trigger (a stored derived value, a forbidden read, a request that differs) the delay is the exposure window. I ask the founder, through chief-of-staff, whether a flag-off withdrawal on a privacy or child-safety trigger may be pre-approved (batch 5 §11.6 item 7). That is the founder's call; I flag it as the most useful single control for the minors question.

### Q-P5. Which `ReasonFacts` may a reason line show? **Narrower than proposed. Own-action facts about a specific lesson are allowed; tallies, rates and anything that grades are not.**
The EDD proposes "counts of the learner's own actions only", with the example "you got 2 of 3 first predictions right in probability". I refuse that example and its class.
- **Allowed fact classes:** (a) a **named lesson the learner completed** ("you finished *X*"); (b) a **count of lessons completed** in a subject or concept ("you've finished 3 lessons on this idea"); (c) **catalog relations** ("*Y* builds on *X*"). These are completion events, are not a measure of ability, and are visible to whoever holds the device only as lessons they already see in the feed.
- **Refused:** any count, ratio or list of **right/wrong predictions** ("2 of 3 right", "you missed", "you got X wrong") as a reason line. It is a performance tally (AMD-008 M2/gate P3.2 spirit: P4 of the model ruling forbids a stored count of right predictions; showing a computed one on a card is the same object made visible), it can be read over a shoulder on a shared family device, and with no off switch a 13 to 15 year old cannot remove it. Also refused: `pKnown`, `estimate`, any probability, any trait ("strong in", "you know", "you struggle with", "behind"), comparison to other learners, the age band, time gaps (`gapDays`), pressure or urgency language.
- Copy for `domain-estimate` and `concept-known` is the risk, since those codes come from an estimate that predictions move. Their lines must state **only the completion or catalog fact** above ("you finished a lesson on this idea"), never the inferred state ("you already know this"). Whether even that is true for every card is F6's and RC's to prove; I only set the privacy ceiling. My earlier P3 allowed "you missed X on revisit" as a statement of what the learner did on one lesson; with no off switch I withdraw that allowance for website reason lines (it stays available elsewhere, for example a revisit card the learner is already answering).
- **E10.** `reason-copy.ts` is checked by a test against a deny-list (the words and number patterns above, plus any `%`, "of N right", "wrong", "missed", "know", "strong", "weak", "behind", "most people") and against an allow-list of fact slots (lesson title, count of completions, concept name). A line that interpolates a value outside those slots fails. No numeric value derived by `rank` is passed to the copy layer at all (the EDD says minus what the copy rules forbid; make it a whitelist, not a minus).

### Q-P6. Signed-in learners: only the local record, never the server `progress` row? **Confirmed as designed; made a condition.**
- **E11.** The ordering path imports no `src/lib/server/**`, no accounts client, makes no call to `/api/account/*` (a signed-in flag may not change the order either: it is an input I would refuse, section 2 of the model ruling, and signed-in status is a proxy for "has an age band"). Test: T4 adds `signedIn` and any `ageBand` value to the variation set; plus a static import-graph check on `new-lesson-order.ts`, `reason-copy.ts` and the generated module (no `server-only`, no accounts import, no `fetch`, no `localStorage` outside the Feed's existing `loadProgress`). The EDD-008 merge writing the server history into `s3c:progress:v1` is the only way server data reaches ordering; I accept that as D1's existing behaviour.
- A signed-in learner's history, once merged into the local record, is visible to ordering on that device, including a shared one. Same as revisits today.

### Q-P7. N3 forbidden list for the serving layer: anything else needed? **Yes. Add these to T4's variation set.**
`FORBIDDEN_INPUTS` (model.ts line 109) plus: `settings`, `personalization_on`, `subjects`/`statedSubjects`, `less_of`/`lessOfThis` (stated choices are **not read** under always-on; ignoring them is a product point for head-of-product, not a privacy gap), `persona`, `ageBand`, `signedIn`/session/account state, `s3c:events:v1` (the local event log holds `dwellMs`, which is forbidden), `s3c:origin:v1`, `s3c:ageband:session`, URL query and hash (including `revisitMinutes`), `document.referrer`, `navigator.*`/`screen`/`matchMedia`/timezone/locale, wall-clock readings other than the single `now` passed to `rank` (no hour of day, weekday, or "days away"), and any extra field on a progress record other than `completedAt`, `predictedCorrectly`, `recalls[].at`, `recalls[].correct`. The EDD's step 1 builds the history field by field, which I accept; keep the tests, and add the control the EDD names (flipping one `predictedCorrectly` must change the order).
- **E12.** T4 is part of `npm run check`, not manual. My earlier T1 condition (the N1/N3 tests "pass when run, not enforced") is not repeated here: the EDD puts T1 to T13 in check. Hold it to that. T11 and T1c need a build, so they run in `verify`; say which tests are which in the PR.
- Also minimise: build `history` only from slugs present in `PILOT_DIMS` if `rank`'s output is identical (assert it), so non-pilot completions do not enter the ordering call. A recommendation, not a condition.

## Other findings

1. **The EDD's counters (§7, §8.2: "cards moved per day by reason code", W-1760) cannot be produced without a client report.** Nothing on the server knows which card was moved. A report from the device of a reason code or a "moved" marker is a derived value leaving the device, which N1 refuses ("not to the beacon or exp"), and which the EDD's own G-3 and non-goals exclude. My N5 ruling allowed counters "by reason per day" without saying how the device would report them; **N1 and N5 conflict on that point, and I wrote both.** Ruling: N1 wins. W-1760 may not build a client-reported counter on this EDD. If analytics-steward wants one, it is a new read (candidate shape I would consider, not pre-clear: a closed-enum event with no slug and no identifier, k >= 20 cells, flag-on traffic only). Until then the EDD's "after release" signal is CI plus review plus reports only, and the release note says live effect is unmeasured.
2. **Shared devices.** The personalised order and the reason lines reveal completed-lesson history to whoever uses the device next. Revisits already do (D1 has no in-app control: inventory gap, section 8). I accept this under the Q-P5 limits and ask that the privacy note on the lesson trust sheet or the site's data page says progress is kept on the device and reorders the feed. That sentence is a claim (copy) for head-of-product and RC, and it is a lawyer-visible fact for the "no way to turn it off" question.
3. **Subject chips as a partial exit.** Subject-filtered feeds serve the default order (EDD §5.4). I do not rely on that as a control and counsel should not be told it is one: it is not discoverable as an opt-out and only covers a chosen subject.
4. **Cold start is the same for every new device and uses no learner data.** No privacy objection. The conflict is about truth of the intro copy and the protected QA test (W-1764, Q-H1), not privacy. I note only that a cold-start card that is "moved" still needs a true line, and that its line may not imply the order is personal.
5. **Failure fallback** (default order, no lines, no logging) is right. The over-budget branch makes personalisation depend on device speed; no privacy issue, but a timing branch must not be reported anywhere (E3).
6. **Settings API.** `personalization_on` stays unbuilt-on. Condition **E7**: the ordering path must not read it (T4), and no learner-visible UI, copy or documentation may imply the column controls the feed. If the settings API ever ships, an explicit `false` stored there has no effect on this ordering, and that mismatch would be a finding I must be told about first.
