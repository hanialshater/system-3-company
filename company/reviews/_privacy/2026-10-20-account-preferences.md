## Save, off, reset and account isolation

1. **Explicit action.** Loading `/`, opening onboarding/settings, changing a checkbox in a draft, signing in, completing a lesson and background refresh never write preferences. A clearly named Save action commits the displayed draft; enabling matching is explicit opt-in, not a checked-by-default suggestion. Anonymous users get canonical behavior and, at most, an ephemeral draft: no preference local/session storage, cookies, indexedDB or server write. Accounts feature off returns404 before session/database access and stores nothing. No anonymous preferences are silently adopted at sign-in.
2. **Off/reset semantics.** Only personalizationOn===true permits matching; null/false/error/unresolved auth/settings use the canonical default. Disable immediately stops matching locally and submits an explicit false marker. Reset atomically sets false, subjects[], lessOf[], experiences[], challenge:null and clears the local draft; it removes choices while retaining the protective opt-out marker. “No storage while off” means no automatic or derived writes, not refusing the explicit disable/reset transaction itself. Do not persist disabled drafts. A failed save/off/reset must be visibly unsaved/retryable, never shown as cross-device success. Do not promise that other devices have changed before server acknowledgement.
3. **Authentication and PC10.** Only `/api/account/settings` GET/PUT; user ID comes solely from the verified session. PUT requires the existing trusted same-origin/JSON checks **and** x-s3c-account matching the opaque server tag for that session. Missing/mismatched tag returns409 and writes nothing. A tag is a binding check, never an auth substitute. Do not widen cookie scope beyond /api/account or accept a user ID/tag as authority in a body/query. Use the trusted deployment origin helper; arbitrary forwarded-host input must not expand accepted origins. Fixed errors/log text only, no pg message/detail, request body or choices.
4. **Reads and async lifecycle.** GET/PUT responses are private no-store; each GET reads the current account row, never a module/global account-row cache. Client preference state is memory only, keyed by the authenticated account tag and a request epoch. Capture tag/epoch before a request; ignore stale GET/PUT responses after sign-out/account change or a newer reset/save. Cancel where possible. Never display accountA choices/order/reasons under accountB or anonymously, even briefly. On409 clear active account preferences and stop retrying the old write. Same-origin credentials alone do not prevent the account-switch race. Bind read responses to the session tag (or validate against a fresh current account epoch) as well as protecting writes.
5. **Cross-device freshness.** Refetch on authenticated load/account change and when returning to the feed/settings after a visibility/focus transition; define a bounded open-tab refresh if continuous cross-device propagation is promised. Default ordering while freshness/auth is unresolved. No persistent cache and no stale PUT replay. A settings-read failure must not restore an older enabled snapshot. Explain that acknowledged choices follow the account and may take a refresh on another device; do not claim real-time sync without implementing it.
6. **Concurrency.** Preserve the existing per-key atomic SQL rule. A subjects/experience/challenge edit must not resend an unchanged stale personalizationOn:true and undo an off from another tab. Only a deliberate enable control/action may send true; partial preference writes omit that flag unless the person changed it. Existing merge keeps the account's lists, never unions inferred/device tastes, and either side false stays false. Extend those rules to the new fields in one statement/transaction. No read-modify-write whole-row race. Do not add timestamps merely to resolve this; compare/lock or per-key atomic writes suffice.
