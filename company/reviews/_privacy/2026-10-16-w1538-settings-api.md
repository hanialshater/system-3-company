## Conditions

- **D2a (new, must fix before the table is applied to a real learner).** `handleSettingsPut` reads the row, computes the whole next row, then upserts all four columns (`UPSERT_SQL`). Two overlapping requests lose an update: PUT A sets `personalizationOn:false`; PUT B (`subjects` only) read the row before A wrote, then writes its stale `personalizationOn:true` back after A. The learner's explicit off is silently reversed, which D2 and G3 exist to prevent. Window is small (two tabs, or a retried request) but the failure is on the protective setting and invisible to the learner. Fix options, engineer's choice: (a) upsert only the columns the request carries (per-key `COALESCE`/`CASE` in one statement, so there is no read-modify-write for `set`); (b) a transaction with `SELECT ... FOR UPDATE` once the db helper supports one. For `merge`, the "either side false gives false" rule must also be decided inside one statement or transaction. Add a test that interleaves a stale-read PUT and asserts `false` survives. I would accept (a) for `set` plus (b) or a single-statement rule for `merge`.
- **B2a. Mount path.** Moving the route to `/api/account/settings` is **fine and changes nothing in my ruling**: B2 means "the settings PUT handler is the only code that writes the table", and the path in my wording was a name, not a requirement. Moving also keeps P6.2 (cookie scoped to `/api/account`), which I prefer to widening the cookie path; widening it would be a new privacy read. Condition: in the same change, update the `ROUTE` constant in `tests/settings/settings-only-put-writes.test.mjs` and the comments citing the old path, and have the scan fail if a route file remains at `src/app/api/settings/`. (The existing import scan already fails any second importer of the handler or store; the stale-file check closes the leftover-route case.) I will treat "only `PUT /api/account/settings`" as the B2 text from then on.
- **B2b. Unverified-at-wiring.** When `settingsDeps()` is filled in, the diff comes back to me (or a one-line confirmation) for: `userId` helper returns the session user only (no query parameter or header fallback), `enabled` reads the flag per request, `log` is not passed a body or error text.
- **B3 (carried).** Before the table is applied anywhere real: the `DELETE FROM settings WHERE user_id = $1` line in the deletion transaction, `settings` in `tools/db-deletion-check.mjs` expecting 0, and the export block, all on the accounts branch (patches in the API note §5). When the deletion file lands, add it to `DELETE_ONLY` in the B2 test in the same change. Owner: backend-engineer.
- **B4a.** At wiring, check the platform does not log request bodies for this route (Vercel log drains, any Sentry-style capture). Request URLs carry no choices (they are in the body), which is correct; keep it that way (no `?subjects=` GET variant).

## Smaller points, no condition

- Body size is checked after `req.text()` as well as by `Content-Length`; fine at 16 KB (platform caps the body).
- Origin check requires a same-host `Origin` and refuses `same-site`/`cross-site` Sec-Fetch-Site; that matches ADR-008 C7. A hostile page cannot set `x-forwarded-host`.
- 401 for signed-out, 404 when the flag is off: no existence leak that matters.
- `settingsCatalog()` memoises published content only; not learner data, so D2's "no cache" is not touched. Lesson slugs include drafts; ids are not secret.
- Export includes stale ids (the learner's copy of the row). Agreed.
- Nothing aggregates over `settings` (SS5); the scan covers SQL writes only, not `SELECT ... GROUP BY`. If anyone proposes a "share with personalization off" count, the query text still comes to me first (k >= 20).
