## 1. Production cannot reach child_process: holds

`runSim` returns `readPrecomputed` as its first statement when `simLocal()` is false, before any key, lock or spawn code. `simLocal` is `NODE_ENV !== "production" && HQ_LAB_PRECOMPUTED !== "1"`: the env var can only turn live runs off, never on, and NODE_ENV=production alone is enough to force precomputed. The reader imports only node:crypto, node:fs, node:path, node:zlib and ./hq-personalization (types plus `precomputedLine`); it has no path to execFile. The server module still imports `execFile` statically, so the code is in the bundle, but only reachable past that guard. The test spy (with a control that proves it sees a live run) covers the behaviour, not just the text. Accepted.

## 2. Fail closed and manifest checking: sound

- Every read goes through `readListed`: the name must match the FILE regex (fixed folder layout, no `..`, no absolute path) and be a key of `manifest.files` (`Object.hasOwn`, so `__proto__` and `constructor` fail), then the sha256 of the bytes must equal the manifest value. Missing file, wrong hash, bad gzip, bad JSON, wrong schema, trace not matching the requested persona/policy/seed: each returns a plain "unavailable ... Nothing was run" message; unknown errors collapse to "unexpected read error". No path falls back to live. 11 fail-closed cases in the new test.
- Requests outside the stored set get a refusal naming what is stored; `saved` is refused.
- Error text echoes only the manifest-relative name, no absolute path.

Nits:
- **H1-N1.** The manifest is not itself hashed, so the check proves the data files match the manifest, not that the manifest is the one that was generated. In a git-committed folder that is the right strength (git is the integrity), and the check catches partial or corrupt deploys. Say so in the README so nobody reads it as tamper-proofing.
- **H1-N2.** A run entry's `days` is matched from the manifest but not compared with the trace's own days (persona, policy, seed are). A hand-edited manifest could label a 7-day trace as 3 days. Low risk (the generator writes it); add `t.run.days === req.days` if the field exists in the trace.
- **H1-N3.** Compare documents are checked for schema and `rows` only, not for persona/seeds/days. Same remark.

## 3. The 0.8 MB data folder in the bundle: traced, with one caveat

The reader builds paths as `path.join(root, PRECOMPUTED_DIR, rel)` with `root = process.cwd()` and a non-literal `rel`. I expected the file tracer to miss that, so I built it: it did not miss it. Both entry points list all 59 files, and the folder is 924 KB on disk. Caveat (**H1-N4**): this depends on the tracer's handling of `path.join(cwd, const, var)`, which is heuristic and has changed between Next versions and between webpack and Turbopack; nothing pins it. If a later upgrade drops the trace, production fails closed ("manifest.json is missing") instead of breaking, which is the right failure, but it would be a blank lab. Cheapest guard: `outputFileTracingIncludes` for the two routes in next.config.mjs (a config change, so its own review and no new dependency), or a test that reads a built `.nft.json` when `.next` exists. The author's "not checked on Vercel itself" is accurate; I did not check there either.

Size: 42 gz traces average about 17 KB, plus 14 comparisons. Well inside a function bundle. Each data read is a synchronous read plus sha256 plus gunzip of a file at most 30 KB; the per-process index cache holds manifest and meta only. No concern.

## 4. Staleness story: honest on the page, not yet enforced

The page prints the inputs commit, its date, the model version, seed and days. `--check` is deterministic and exits 1 naming the files. The generator refuses uncommitted inputs, so the date is a real commit.

- **H1-N5 (the real gap).** `--check` is manual. It is not in `npm run check`, `verify`, a test or CI, so a model change that does not regenerate the folder ships a released lab that shows old numbers under an accurate old date. The banner prevents a false claim, but nobody is told. Options, owner personalization-engineer with tools-lead: a test that compares `inputsCommit` with `git log -1 -- <INPUTS>` and warns (a full regenerate at 45 s is too slow for check); the git-log comparison is cheap but fails in a shallow clone (the same cause as the three releases.test.mjs failures), so it must skip when git cannot answer. Until then, name the regenerate step in the release runbook.
- **H1-N6.** gz output is byte-deterministic for a given zlib. A different Node/zlib version can change compressed bytes, which would show every trace as STALE with no data change. Hashing the decompressed content in `--check` (while keeping the file hash for serving) would avoid false alarms. Not urgent.

## 5. Privacy test changes: not weakened

- Scope grew (reader, data folder, generator); REQUIRED gained four files, so a rename fails instead of shrinking the scan. FORBIDDEN gained `@import` and `image-set(`, closing my U1 nit. All existing rules still apply to every file.
- The relaxation: import rules apply to code files only (`.js/.ts/.tsx/.mjs/.cjs/.css`). That is correct for JSON (a `"from"` key is not an import) and does not exempt anything executable. `.gz`, `.json`, `.md` still get fetch, /api, storage, cookie, `s3c:` and url() rules. gz is decompressed first and an unreadable gz is itself a finding.
- Allowlist gained node:crypto, node:zlib and ./hq-personalization-precomputed. The first two are pure and could be needed only for the reader, but the allowlist is per-repo not per-file, so any lab file may now import them. **H1-N7:** harmless (no I/O or network), but note the trust-list rule (ruling L2) now also covers the reader: it is both scanned (in SCOPE) and trusted by name, so an edit to it is read under L2 as before. This review is that read.
- Nine new planted breaks (3 CSS, 3 in the reader/generator, meta, gz trace); each must fail under its named rule and the gz one is planted compressed. The 47 break count matches the file.
