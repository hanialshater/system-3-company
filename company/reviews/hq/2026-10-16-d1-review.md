## Checked and fine

1. **Lock semantics** (src/lib/hq-personalization-server.ts `runSim`). Identical request (key = root + cliArgs) returns the same promise; a different one gets `{ok:false, error:BUSY}`; `.finally` clears `inFlight` on every settle. `spawnSim` always resolves (every execFile exit, timeout kill and bad JSON goes through the callback), so the lock cannot stick. A synchronous throw inside the Promise executor would reject, and `.finally` still releases. The key is set after `spawnSim` is created, and nothing awaits between, so no race in single-threaded JS.
2. **Module instances.** The page (src/app/hq/personalization/page.tsx) and the route import the same file. Next bundles server components and route handlers as separate entries, so in practice there are two lock instances (one per page/route), as the file comment says. Consequence: the guarantee is "at most one per entry, so at most two", not one. That is acceptable for a local-only lab; the comment is honest. Not worth a `globalThis` singleton.
3. **Meta cache key.** Newest mtime of every file under company/personalization/model (skipping `out` and `node_modules`) plus the mtime of sim/out/traces. hq-cli `meta` imports only from inside that folder (model.ts, personas.ts, sim/*) and lists traces by name only (`savedFiles`), so the key covers its inputs. Directory mtime changes on add/remove, not on in-place overwrite of a trace, but meta shows names only, so this is fine. Failures are not cached. The cached object is shared by reference; the page and route only serialize it.
4. **CHILD_ENV.** The child is `execFile(process.execPath, [absolute script, ...args])`: no shell, no PATH lookup, so no PATH is needed. grep of model/model.ts, sim/hq-cli.mjs and self-check.mjs finds no `process.env` and no child spawn in the CLI. Node's TS type stripping needs no flag on 22.18+. The test runs a real child under the minimal env and passes. The `as unknown as NodeJS.ProcessEnv` cast is only a type workaround (Next types `NODE_ENV` as required); it does not change runtime. Privacy DoD child-env point is met.
5. **429 mapping.** BUSY maps to 429, other failures to 422, bad parameters to 400. The client reads `j.error` on any non-ok, so the message shows. Correct status for "try again later".
6. **Labels** (Personalization.tsx). All changes are text/aria only: "Simulated persona(s)", "all six simulated personas", caption, fingerprint region, heading, legend. No logic touched.

## Nits (none blocks)

- N1. The page's `meta` call goes through the same lock. If a different run is in flight in the same module and the meta cache is cold, the page renders the BUSY text as its error with no retry. Low odds (page and route are separate instances in Next), but `meta` is cheap and read-only: let a cache miss on `meta` bypass the lock, or retry once.
- N2. `out.error === BUSY` string compare couples the route to message text. A `busy: true` field on the result would be sturdier. Also no `Retry-After` header on the 429.
- N3. The test never exercises "released on error" (a failing run followed by a new one). Add one: run an unknown persona, then a valid request, and assert the second is not BUSY. The existing "lock is released" assertion only covers success.
- N4. The minimal env would break on Windows (needs `SystemRoot`). The lab says Node 22.18+ and local; if Windows dev matters, pass `SystemRoot` through when set.
- N5. Joined requests share the first caller's 90 s timeout. Fine; just note it.
